#### 2.6.1 审计哈希链复核（FR-AUD-002/003 · 本轮修复 5 处缺陷）

**触发点**：收尾自检时 `/api/audit/verify-chain` 对**应用自己写入的数据**报「第 1 条被篡改」。
按"不轻信被测代码"的口径查了三层，结论是：**检测器本身正确，但哈希反查与 detail 还原有缺陷**。

定位方法（依次排除）：

1. **独立复算**：把 `aud_logs` 全量导出，按 `canonicalize` 规则用 Python 重算 SM3 与落库 `record_hash` 比对 —— 200 条中 199 条一致，
   唯一不一致的那条，把它的 `action` 换回 `auth.login` 后**精确复现**落库哈希，证明该行只是单字段被改过（早前篡改检测实验的残留），检测结论属实。
2. **行为探针**：把 `jsonToDetail`/`canonicalDetail` 原样抽成独立程序喂真实 detail 文本，直接看到 `{"key": "v"}` 被解析成 ` "key"= "v"`。
3. **端到端复现**：用接口写一条自己的记录，立即校验它 —— 修复前必报篡改，修复后为 ok。

| # | 缺陷 | 影响面 | 修复 |
| --- | --- | --- | --- |
| 1 | **`String.trimStart()/trimEnd()` 在本机仓颉 SDK 1.0.5 上是空实现**（`"  abc  ".trimStart().size == 7`），故 `{"k": "v"}` 被还原成 ` "k"= "v"` | 全部 detail 非空的记录（实测 18 条）误报篡改 | 新增 `ams.kernel.util.trimSpace()`，替换全仓 16 处误用 |
| 2 | `AuditAction.fromCode` 与 `code()` 有 4 个动作用词不一致：`share.create`↔`acl.share_create`、`share.access`↔`acl.share_access`、`kms.key_rotate`↔`crypto.key_rotate`、`archive.batch`↔`archive.batch_operation` | 反查退化为 `unknown` → 哈希不符（实测 14 条） | `fromCode` 同时接受新旧码（兼容历史数据） |
| 3 | `toResult(2)` 返回 `Success`（应为 `Denied`） | 全部 `result=2`（拒绝类）记录误报，实测 20 条 | 补 `2 → Denied` |
| 4 | `toActorType(3)` 未处理（退回 `User`） | `actor_type=3` 记录会误报（当前无此类数据，防御性修复） | 补 `3 → Service` |
| 5 | `MemorySessionStore.get()` 用 `HashMap[sid]` 直接读，键缺失**抛异常**（仓颉 `[]` 不返回 Option） | **服务重启后**（会话在内存）持旧令牌的请求返回裸 `500 Internal Server Error` 而非 401 | 先 `contains` 再取，返回 `None` |

- `detailToJson` 按 JSON 规范转义（`"`、`\`、控制字符）：值里的 `"` 会让 jsonb 插入失败、控制字符会被 jsonb 改写为 `\uXXXX`，两者都会让校验时的哈希与写入时不一致；

#### 2.7.1 批量导入附件（FR-IMP-002）：为什么这次能做成

上一轮把它标成「SDK 限制」，依据是 stdx 只有 tar/zlib、没有 `compress.zip`。这个判断只对了一半：
**ZIP 的压缩载荷本身就是 RFC 1951 裸 deflate**，不需要 zip 库也能解开。写了个独立探针实测：

| 输入数据 | `WrapType.DeflateFormat` | `WrapType.GzipFormat` |
| --- | --- | --- |
| 裸 deflate（ZIP 条目格式） | ✅ 45B → 40B 正确 | ❌ ZLIB_DATA_INVALID |
| zlib 封装（RFC 1950） | ❌ | ❌ |

结论：`DeflateFormat` 就是裸 deflate，**deflate 压缩的 ZIP 可以正常解**。剩下的容器解析（EOCD / 中央目录 / 本地头）
是确定性格式，可以手写并逐项测。真正的难点不在「解压」，而在**中文 Windows 打出来的包**：`Info-ZIP`/资源管理器
不打 UTF-8 标志位（bit 11），文件名是 GBK 字节 —— 直接按 UTF-8 解就是乱码，目录名一乱，「目录→条目」映射全错。

实现要点：

| 关注点 | 做法 |
| --- | --- |
| 容器解析 | 自尾向前找 EOCD（容忍注释）→ 中央目录逐条读 → 用本地头的 `data offset` 定位载荷；不信任中央目录里的偏移被篡改的情况，越界即拒 |
| 压缩方法 | `0=store` / `8=deflate` 支持；`9=deflate64`、`12=bzip2`、`99=AES`、加密位（bit 0）一律显式报「不支持」而不是产出乱码文件 |
| 文件名编码 | bit 11 置位 → UTF-8；未置位 → **UTF-8 / GBK 双解码 + 可信度打分**（ASCII/CJK/中文标点/全角/通用标点加权，同分优先 UTF-8）。GBK 表是 87×94 码表（7478 条有效映射）由 `scripts/gen-gbk-table.py` 生成，未分配位落 ASCII `?` 而非 U+FFFD（后者会触发大量 `unsecure character` 告警） |
| 路径安全 | 反斜杠归一、去掉盘符/前导 `/`；出现 `..` 段、绝对路径、Windows 保留名 → 标 skip **但保留原路径**用于展示「哪个条目被拒」（返回空串会让用户看不懂为什么少了文件） |
| 解压炸弹 | 解压时**边解边计数**，超 50 MB/文件立即中止（不是解完再判断）；条目数上限 2000；中央目录声明的大小与实际解出量不一致也中止 |
| 数据完整性 | 边解边算 CRC32 与中央目录比对，不符报「CRC 校验失败（文件损坏）」；UTF-8 结果再做一次合法性校验 |
| 映射规则 | 路径首段 = 条目标题，末段 = 文件名；根目录文件、非 jpg/jpeg/png/pdf、目录名 >200 字节 → skip 并给出人话原因 |
| 幂等 | 上传走 `attachments.upload(..., dedup: false)`：批量导入若走去重，命中时不会为新条目建归属，等于**文件静默丢失** |
| 请求体 | 附件/导入路径放宽到 64 MB，且改为**分块累积**读取（原来单次 `read()` 上限 1 MiB，超了会静默截断，魔数校验还能通过，看起来「上传成功」）；累积时每块**显式逐字节拷贝**，不依赖 `Array[Range]` 是拷贝还是视图 |

两阶段交互（前端 `web/src/views/ImportView.vue`）：

```
选包 → precheck（不写库，真解一遍验 CRC）
        ↓ 返回 {total, match, create, conflict, skip, newTitles[], conflicts[], rows[]}
     映射预览表（每行：路径 / 标题 / 大小 / 动作 / 目标条目 / 说明）
        ↓ 冲突目录逐个下拉指定（或选「仍然新建」）
     确认导入 → 异步任务 → 1.5s 轮询进度 → 错误报告 CSV 下载
```

预检与执行共用同一份 `buildPlan()`（只有 `resolutions` 不同），所以不会出现「预检说将新建、执行却挂到别的条目」。
**未解决冲突直接 409 并点名目录**（`1 个重名目录尚未指定目标条目：清华大学 硕士学位证书`），
而不是留到执行阶段变成一堆行错误让用户反推。

#### 2.7.2 收尾补强（现场「60 个条目的包解析失败」）

现场用真实包（60 个条目）预检时报 ZIP 解析失败，而**同一个包从磁盘直接喂解析器却完全正常**
（探针：`size=6022 eocd=6000 count=60 cdOff=2820 openOk entries=60`）——
说明问题不在解析器，而在**请求体进入解析器之前**。

处置：

| # | 问题 | 处置 |
| --- | --- | --- |
| 1 | 分块读用 `chunk[0..n]` 累积，而缓冲区是**复用**的。若 `Array[Range]` 返回视图，所有分块会指向同一段内存，拼出的 body **长度正确、内容全错** —— 这是唯一能同时解释「size 对得上、解析却失败」的机制 | 新增 `ApiRequest.copyOf()` 显式逐字节拷贝，从语义上消除该依赖 |
| 2 | 预检读 `req.bodyBytes` 原文、提交走 `splitFramed`，两个入口对请求体的解释不一致 | 预检也改用 `splitFramed`（裸 ZIP 与封帧体都接受），主体/分类 query 缺失时回落到封帧 JSON |
| 3 | 预检接口残留早期定位用的 `?debug=1`（把字节数与指纹回显在错误消息里） | 移除 |
| 4 | 前端不校验包大小，用户要传完几十 MB 才拿到 413 | 选包时按 64 MiB 拦截并提示拆包；页内说明标注「单个压缩包 ≤ 64MB」 |
| 5 | 解析侧缺多条目基线用例 | 新增 `testSixtyEntries`（60 条目：全部枚举、路径与内容一一对应、首段=标题）与 `ChunkAccumulateTest`（分块拷贝独立性、跨块还原） |

> 单包 64 MiB 是**能力边界而非疏漏**：请求体在鉴权之前就被读入内存，
> 只对附件/批量导入两个入口按路径放宽，其余接口仍是 1 MiB（见 `api.http.bodyCapFor`）。
>
> 第 1 项的证据链在 `packages/ams-app/tests/importer/probe_test.cj` 的注释里（原为临时探针，
> 现已转为 `ChunkAccumulateTest`）—— 现场结论「解析器没问题、问题在请求体」是从那里定下来的。
