### 7.2 过程中发现并修复的真实缺陷

这几条**都是「实现了但实际不生效」**的类型，单靠单元测试发现不了，
是端到端验证脚本（`scripts/ci/verify-authz.sh` / `verify-password.sh`）抓出来的：

| # | 缺陷 | 影响 | 根因 |
| --- | --- | --- | --- |
| 1 | **中间件在路由匹配之前执行**，`req.pathParams` 为空 | 资源守卫拿不到 `:id` → **对象级鉴权整体被跳过**，任何登录用户都能读写他人条目 | 中间件调了 `router.find()` 却丢弃了 params |
| 2 | 中间件的功能权限判定用**精确匹配** | 持有 `archive:read:any` 的用户读 `own` 范围接口被误拒，Authorizer 根本没机会执行 | 中间件与 `Authorizer.hasFunctionPerm` 逻辑不一致 |
| 3 | 资源守卫用**带归属过滤**的查询 | 被显式授权（`acl_grants`）的用户在守卫阶段就查不到条目 → **FR-ACL-008 端到端不通** | 归属判定被重复做了，且没给显式授权留路径 |
| 4 | 敏感度判定缺少「所有者」路径 | 所有者读自己名下 sensitive 条目被拒 | PRD 明确「high 默认仅所有者可见」，但实现只认显式授权 |
| 5 | `AccessContext` 不区分「本人拥有」与「被授权代管」 | 无法实现「所有者天然可见、代管人需显式授权」 | 两者混在一个集合里 |
| 6 | 弱口令字典**没有数据源** | 「弱口令字典」检查形同虚设 | `PasswordValidator` 构造时传入的数组在生产中不存在 |
| 7 | 哈希链的 `occurredAt` 精度不一致 | 链校验误报「链断裂」 | 落库用应用层毫秒，校验时从 `TIMESTAMPTZ` 换算会四舍五入差 1 |

#### 过程中的技术约定（后续改这块代码请沿用）

| 约定 | 原因 / 现状 |
| --- | --- |
| `st.query()` 返回 `QueryResult`，须经 **`readRows()`** 转 `RowSet` 才能 `.all()` | 直接按 RowSet 用会报 `mismatched types` / `all is not a member of QueryResult` |
| 布尔列以 **SQL 字面量 `TRUE`/`FALSE`** 拼入，不由驱动绑定 boolean | 沿用 `RoleRepo.createRole` 既有写法；取值域固定，无注入风险 |
| `RowData.size` / `Array.size` 是**属性**不是方法 | `arr.size()` 会报 `no matching function for operator '()'` |
| `StringBuilder.append()` 返回 `Unit`，**不可链式** | `sb.append(a).append(b)` 会报 `undeclared identifier 'append'` |
| `HashMap` 用 `m[k] = v`，**没有 `.put()`** | `.put()` 报 `'put' is not a member of class HashMap` |
| 跨类不可调用别的类的 `private static` 成员 | 如 `FieldDefRepo` 不能调 `ItemRepo.bindStr`，已在本地提供同语义实现 |
| `ams-app` **可以**依赖 `ams-core` | 构建拓扑中 ams-core 先于 ams-app，`FieldTemplateService` 已验证可行 |
