# 14 · 家庭成员邀请（设计 + 方案评估）

> 本文由多份同源文档合并而成，保留原始核对/设计记录，章节内标注「原 N」。历史变更见 CHANGELOG.md。

## 设计（原 14）


> 对应需求：**SC-12**（家庭成员邀请与轻量协作）、**FR-ACL-010**（家庭成员邀请：邀请码/二维码；成员仅可见显式授权内容）
> 关联需求：FR-ACL-001~009（授权共享与回收）、FR-ACL-013（权限预览）
> 状态：**设计稿（未实现）** · 版本：v1 · 日期：2026-10-29
> 适用代码基线：`main`（P2 进行中，已完成 11/23）

---

### 0. 一句话结论

家庭协作的**唯一安全底线**是：**成为家庭成员 ≠ 获得任何数据访问权**。
成员能看到的每一条数据，都必须来自一条**显式、可过期、可撤销、留痕**的授权记录。
邀请只解决「把人拉进组」，绝不顺带解决「给他看什么」。

---

### 1. 背景与目标

#### 1.1 业务背景

现有系统已支持「本人档案」与「机构内按角色/主体授权」（FR-ACL-001~009）。
但家庭场景（配偶代办、子女代管老人证件、父母查看子女学籍）缺少一条**低门槛、可解释、可收回**的协作路径：

- 让家人注册成机构用户并分配角色，过重且语义错误；
- 直接把账号口令给对方，等于放弃追责与撤销能力；
- 公开共享链接（FR-ACL-011）只读且面向「任何人」，不适合长期家庭协作。

#### 1.2 目标

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G1 | 用邀请码/二维码把家人拉入「家庭组」 | 生成 → 扫码/输码 → 入组，全程 ≤ 3 步 |
| G2 | 入组后**默认什么都看不到** | 新成员登录后条目列表为空 |
| G3 | 所有者按「条目 / 分类 / 主体」显式授权 | 授权后成员仅能看到被授权范围 |
| G4 | 授权可设有效期、可随时撤销、到期自动失效 | 撤销/到期后下一次请求即 403/404 |
| G5 | 全过程可审计、可举证 | 邀请、入组、授权、撤销、移除均有审计事件 |
| G6 | 邀请凭据不可猜测、不可重放、不可长期有效 | 见 §7 威胁模型与控制 |

#### 1.3 非目标（明确不做）

- ❌ 家庭成员之间的**写协作**（共同编辑同一条目）——P3 再议；
- ❌ 家庭组内的**审批流**（如「子女申请查看，父母审批」）——P3 再议；
- ❌ 跨家庭组的数据共享与转授权；
- ❌ 通过邀请直接获得任何管理类权限（`system:*` / `acl:manage` / `audit:read`）。

### 2. 术语与角色

| 术语 | 定义 |
| --- | --- |
| 家庭组（Family Group） | 协作的最小单元。一个用户可创建/加入多个组（如「我的小家」「父母家」） |
| 组所有者（Owner） | 创建者。唯一有权邀请、授权、移除成员、解散组 |
| 组管理员（Manager，可选） | 由 Owner 指定，可邀请与授权，但**不能**移除 Owner / 解散组 |
| 家庭成员（Member） | 被邀请入组者。**默认零可见**，仅能读取被显式授权的内容 |
| 邀请（Invite） | 一次性的入组凭据，含 code（人输）与 link（扫码）两种载体 |
| 授权（Grant） | 一条 `acl_grants` 记录：`(grantee, 资源类型, 资源 ID, 权限, 有效期)` |

> **角色与系统 RBAC 的关系**：家庭角色是**组内角色**，不写入 `sys_user_roles`。
> 成员的全局权限仍然只有系统角色（默认 `user`）。家庭组内的可见性由 `acl_grants` 决定，
> 避免「入组即提权」这类结构性风险。

---

### 3. 核心安全原则（设计约束，不可妥协）

1. **默认拒绝（Default Deny）**
   无授权 = 不可见。列表查询必须**先算可见集合**再查数据，禁止「查全量再过滤」。
2. **显式授权（Explicit Grant）**
   授权必须指名「谁 + 什么资源 + 什么权限 + 到什么时候」，缺一不可。
3. **最小权限（Least Privilege）**
   成员默认仅有 `archive:read:own`（读被授权内容）；无写、无删、无导出、无分享。
4. **凭据不可猜测（Unguessable）**
   邀请 code 由 CSPRNG/密钥派生，≥ 40 bit 熵；链接 token ≥ 128 bit 熵。
5. **短时效 + 一次性（Short-lived & Single-use）**
   默认 15 分钟、1 次；可配上限 24 小时、10 次。
6. **不可枚举（No Enumeration）**
   邀请校验失败、被邀请人不存在、已入组，对外**统一错误文案与状态码**。
7. **可撤销（Revocable）**
   邀请可撤销；成员可移除；授权可撤销；三者的生效时间都是「下一次请求」。
8. **全程留痕（Auditable）**
   邀请创建/接受/撤销、成员加入/移除、授权创建/撤销，全部落审计链。
9. **不越权授权（No Privilege Escalation）**
   授权人只能授出**自己拥有**的权限；被授出的权限不得超过授权人的数据可见上限。
10. **数据最小化（Data Minimization）**
    成员可见的字段按 `sensitivity` 逐级掩码；附件、扩展字段默认不随条目授权自动可见。

### 4. 数据模型

#### 4.1 新增表

```sql
-- 家庭组
CREATE TABLE IF NOT EXISTS fam_groups (
    id          BIGINT       PRIMARY KEY,
    name        VARCHAR(64)  NOT NULL,
    owner_id    BIGINT       NOT NULL,
    status      SMALLINT     NOT NULL DEFAULT 0,   -- 0 正常 / 1 已解散
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    version     INT          NOT NULL DEFAULT 1
);

-- 组成员（组内角色与全局 RBAC 解耦）
CREATE TABLE IF NOT EXISTS fam_members (
    id          BIGINT       PRIMARY KEY,
    group_id    BIGINT       NOT NULL,
    user_id     BIGINT       NOT NULL,
    role        VARCHAR(16)  NOT NULL DEFAULT 'member',  -- owner / manager / member
    status      SMALLINT     NOT NULL DEFAULT 0,         -- 0 正常 / 1 已移除
    invited_by  BIGINT       NOT NULL DEFAULT 0,
    joined_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    removed_at  TIMESTAMPTZ,
    removed_by  BIGINT
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_fam_members
    ON fam_members(group_id, user_id);
CREATE INDEX IF NOT EXISTS idx_fam_members_user ON fam_members(user_id);

-- 邀请（只存 code 的加盐摘要，不存明文）
CREATE TABLE IF NOT EXISTS fam_invites (
    id           BIGINT       PRIMARY KEY,
    group_id     BIGINT       NOT NULL,
    inviter_id   BIGINT       NOT NULL,
    code_hash    VARCHAR(128) NOT NULL,
    code_salt    VARCHAR(64)  NOT NULL,
    target_role  VARCHAR(16)  NOT NULL DEFAULT 'member',
    max_uses     INT          NOT NULL DEFAULT 1,
    used_count   INT          NOT NULL DEFAULT 0,
    fail_count   INT          NOT NULL DEFAULT 0,
    max_fails    INT          NOT NULL DEFAULT 5,
    expires_at   TIMESTAMPTZ  NOT NULL,
    revoked      BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_fam_invites_group ON fam_invites(group_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_fam_invites_expires ON fam_invites(expires_at)
    WHERE revoked = FALSE;
```

#### 4.2 复用既有表

| 表 | 用途 | 说明 |
| --- | --- | --- |
| `acl_grants` | 显式授权（已有，FR-ACL-008） | 新增 `group_id` 可空列，便于「按组撤销」与审计聚合 |
| `sys_audit_log` | 审计链（已有） | 新增动作码见 §8 |
| `arc_items` / `arc_item_fields` | 被授权资源 | 不改结构 |

> **不新增「可见性物化表」**：可见集合始终由 `acl_grants` **实时计算**。
> 物化视图会引入「撤销后仍有缓存副本」的一致性问题，对隐私系统不可接受。

### 5. 邀请流程

#### 5.1 时序（邀请方 → 被邀请方）

```
Owner                     服务端                        被邀请人
  │  POST /family/groups/:id/invites
  │─────────────────────────▶│
  │                          │ 1. 校验 Owner/Manager 身份
  │                          │ 2. 生成 code(8位Base32,40bit) + token(128bit)
  │                          │ 3. 仅存 HMAC-SM3(salt, code) 与 token 摘要
  │                          │ 4. 写审计 invite.create
  │◀── {code, link, qr, expiresAt, maxUses}
  │   （线下/当面告知 code；或展示二维码）
  │                                                      │
  │                                                      │ 扫码打开 /invite/:token
  │                                                      │──────────────▶ GET /family/invites/:token
  │                                                      │◀── {groupName, inviterNick, expiresAt}
  │                                                      │ 输入/确认 code
  │                                                      │──────────────▶ POST /family/invites/accept
  │                          │ 1. 校验 code 摘要 + 有效期 + 次数
  │                          │ 2. 写入 fam_members（role=member）
  │                          │ 3. used_count+1，达上限即失效
  │                          │ 4. 审计 invite.accept
  │                          │◀── {groupId, role:"member"}
  │  （此时成员可见 0 条 —— 默认拒绝）
```

#### 5.2 邀请码 vs 二维码

| 载体 | 形式 | 优点 | 风险 | 控制 |
| --- | --- | --- | --- | --- |
| 邀请码 | 8 位 Base32（去掉 0/O/1/I/L） | 可口头/短信传达 | 可能被肩窥、截图转发 | 15 分钟 + 1 次 + 失败上限 |
| 二维码 | `https://<host>/invite/<token>` | 扫码即达，体验好 | 截图外流、群聊转发 | 同上 + 短 TTL + 可撤销 |

> **二维码不含任何 PII**（不含姓名、手机号、组名明文），只含随机 token。
> 扫码落地页必须带 `Referrer-Policy: no-referrer`，避免 token 经 Referer 外泄。

#### 5.3 边界与冲突处理

| 场景 | 处理 |
| --- | --- |
| 邀请自己 | 拒绝（400，文案不区分「自己是 owner」与「自己已入组」） |
| 已是同组成员 | **幂等成功**（不重复插入，`used_count` 不增加），返回 `alreadyMember = true` |
| 已在**其他**家庭组 | 允许（一个用户可属于多个组） |
| 邀请已过期 / 已撤销 / 次数用尽 | 统一 `404`，文案「邀请无效或已过期」 |
| code 连续错误 ≥ max_fails | 邀请立即 `revoked = TRUE`，后续一律 404 |
| 组已解散 | 拒绝，404 |

> **判定顺序（`acceptInvite` 实际实现，2026-10 落地时调整过）**：
> `token 定位 → **成员身份** → 状态有效 → code 正确 → 原子消耗次数 → 入组`
>
> 「成员身份」必须排在「状态」之前。原因是默认 `maxUses = 1`：家人第二次点同一个链接时，
> 邀请刚好已被他自己用尽，若先判状态就会看到「邀请不存在」——
> 而他明明已经在组里。这种「加入了却说邀请无效」的反馈会让人反复找邀请人重发。
> 提前判定不泄漏信息：能走到这一步说明**持有 token**（凭据已具备），
> 而「你在不在这个组里」对本人本来就不是秘密；非成员仍拿 404。

### 6. 授权模型（成员可见性的唯一来源）

#### 6.1 授权粒度

> ✅ **已决策（docs/14-家庭成员邀请.md（方案评估章节） §5 · 方案 B）**：落地为**主体 + 条目两级**，
> 「分类」不单独成档，而是**同一主体内按分类收窄**。
> 理由是现有 `acl_grants.subject_id` 为 `NOT NULL`，`Grant.covers()` 的分类匹配
> 之后仍要求同主体 —— 「跨主体按类目共享」在当前数据模型上根本不成立；
> 若为它改造核心 ACL 表（放开 `subject_id` 可空），会让每一次既有授权判定都多一个分支，
> 收益远小于风险。分类收窄已经覆盖「各类目分享给不同家人」的真实需求。

| 粒度 | 落库形态 | 示例 | 说明 |
| --- | --- | --- | --- |
| 主体 | `item_id` NULL、`category` NULL/0、`subject_id` = 主体 | 授权「母亲」主体下全部条目 | 最常用，适合代办 |
| 分类（收窄） | `item_id` NULL、`category` = 分类码、`subject_id` 必填 | 授权「母亲」主体下的「健康信息」 | **同主体内**按类目收窄，不跨主体 |
| 条目 | `item_id` = 条目 ID、`subject_id` 必填（用于归属校验） | 授权单张「房产证」 | 最细，适合单点共享；服务端校验条目确属该主体 |

> **不做字段级授权**（FR-ACL-014 为 P3 预留）。字段可见性由 `sensitivity` 与成员数据上限决定，不单独授权。
>
> **为什么不是「跨主体分类」**：那需要一个与主体无关的授权轴，等于把「一条授权覆盖 N 个主体」
> 引入 ACL 核心，历史判权、审计追溯、撤销语义都要重做一遍。真要跨主体批量分享，
> 正确做法是**每个主体各授一条**（前端已提供主体选择器，操作成本可接受）。

#### 6.2 授权记录字段

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `grantee_id` | 被授权用户 | 必须是本组成员 |
| `granted_by` | 授权人 | 必须是 Owner/Manager |
| `subject_id` | 档案主体 | **NOT NULL**；授权人必须拥有该主体 |
| `item_id` | 条目 ID | 可空；非空时校验条目确属 `subject_id` |
| `category` | 分类码收窄 | 0 = 不限（主体级）；>0 时要求同主体 |
| `perms` | `read`（本期仅读） | 不含 `write`，固定 `archive:read:own` |
| `expires_at` | 到期时间 | 可空（永不过期） |
| `revoked_at` | 撤销时间 | 非空即失效 |

> **与初稿的偏离**：初稿写的是 `resource_type` + `resource_id` 两个泛化字段。
> 落地时改成 `subject_id` / `item_id` / `category` 三列，直接复用既有的 `acl_grants`
> 表（不新造一张平行授权表），否则「共享链接」与「家庭授权」会形成两套判权逻辑。
> `resource_type` 现在由 `GrantScope.resourceTypeOf(itemId, category)` **计算得出**
> （条目 > 分类 > 主体），只用于展示与审计，不落库 —— 少一列就少一处不一致。

#### 6.3 可见性判定顺序（服务端强制）

```
1. 用户已认证                     否 → 401
2. 用户在目标家庭组内且 status=0    否 → 403（不区分「不在组」与「已移除」）
3. 取该用户全部有效授权（未撤销、未过期）
4. 目标条目命中任一授权范围？        否 → 403（列表查询则直接不返回）
5. 条目 sensitivity <= 用户数据上限？ 否 → 返回但字段掩码（或按策略 403）
6. 审计（仅当发生「敏感明文」访问时）
```

> **性能约束**：列表查询必须把「授权范围」下推为 SQL 条件（`EXISTS (SELECT 1 FROM acl_grants ...)`），
> 不允许先拉全量再在应用层过滤。授权数超过阈值（如 200 条/人）时走 `acl_grants(grantee_id, resource_type)` 索引。

### 7. 威胁模型与控制

#### 7.1 威胁清单

| # | 威胁 | 攻击面 | 影响 | 控制措施 |
| --- | --- | --- | --- | --- |
| T1 | 邀请码被暴力枚举 | `POST /invites/accept` | 未授权入组 | 40 bit 熵 + 失败上限 5 次 + 按 IP 限流 10 次/分 + 短 TTL |
| T2 | 邀请链接被转发/截图 | 二维码、链接 | 陌生人入组 | 一次性 + 15 分钟 + 可撤销 + 入组审计可追溯 |
| T3 | 入组即提权 | 角色映射错误 | 越权读写 | 家庭角色**不写入** `sys_user_roles`；成员全局权限不变 |
| T4 | 授权越权（授出自己没有的） | 授权接口 | 数据外泄 | 服务端校验「授权人可访问该资源」+「perms ⊆ 授权人 perms」 |
| T5 | 撤销不生效 | 缓存/物化视图 | 撤权后仍可见 | 可见性实时计算，不缓存；撤销写库即生效 |
| T6 | 枚举用户是否注册 | 接受邀请接口 | 账号探测 | 统一错误文案与状态码；不返回「该手机号未注册」 |
| T7 | 邀请 code 泄露到日志 | 访问日志 | 凭据泄露 | 日志只记 invite_id，**绝不记 code/token 明文** |
| T8 | 重放已接受的邀请 | 重放 accept | 重复入组 | `used_count` 原子自增 + 唯一索引 `(group_id, user_id)` |
| T9 | CSRF 伪造授权/移除 | 管理接口 | 越权操作 | Bearer Token（非 Cookie）+ 同源校验 + `Content-Type: application/json` |
| T10 | 成员被移除后会话仍可用 | 会话层 | 残留访问 | 移除时吊销该用户全部会话（`sessions.revokeAll`）+ 授权全撤 |
| T11 | 高敏字段经共享旁路泄露 | 条目详情/列表 | 隐私泄露 | `sensitivity > maxDataLevel` 字段掩码；附件不随条目自动可见 |
| T12 | 审计被篡改 | 审计表 | 无法举证 | 沿用现有 SM3 哈希链 + 审计表仅 INSERT/SELECT（受限角色） |
| T13 | 邀请接口被刷（DoS） | 创建邀请 | 资源耗尽 | 每用户 10 次/小时；全局限流中间件兜底 |
| T14 | 二维码指向钓鱼站 | 二维码 | 凭据被钓 | 链接固定同源域名；落地页展示组名+邀请人昵称供核对 |

#### 7.2 密码学选择

| 用途 | 算法 | 理由 |
| --- | --- | --- |
| 邀请 code 摘要 | HMAC-SM3(salt, code) | 与全仓国密口径一致；code 熵低但短时效 + 失败上限已足够 |
| 邀请 token | HMAC-SM3(服务端密钥, 随机数) 取 128 bit | 不可预测、不可逆；密钥轮换即全量失效 |
| 审计链 | SM3 哈希链（已有） | 与现有 FR-AUD 一致 |

> **不以「加密」代替「摘要」**：邀请 code 不需要还原，只做比对，故用单向摘要。

### 8. 审计事件

| 动作码 | 触发 | 关键字段 |
| --- | --- | --- |
| `family.group.create` | 创建家庭组 | groupId, name |
| `family.group.dissolve` | 解散组 | groupId, memberCount |

| 场景 | 状态码 | 文案 |
| --- | --- | --- |

### 2. 代码现状核查（为什么不能按纸面设计直接开工）

设计稿 §6 假设「三种粒度相互独立，各有 `resource_type` + `resource_id`」。**实际代码不是这样**。核查结果：

#### 2.1 `acl_grants` 表（FR-ACL-008 已落地）

```
id            bigint     NOT NULL
subject_id    bigint     NOT NULL   ← 主体必填，不可空
item_id       bigint     NULL       ← 可选收窄
category      smallint   NULL       ← 可选收窄
grantee_id    bigint     NOT NULL
perm_codes    varchar    NOT NULL
granted_by    bigint     NOT NULL
granted_at    timestamptz NOT NULL
expires_at    timestamptz NULL
revoked_at    timestamptz NULL
revoke_reason varchar    NULL
```

这是「**主体为轴 + 可选用条目/分类收窄**」的模型，**不是**三个平等粒度。

#### 2.2 `Grant.covers()` 的真实语义（`ams-security/src/authz/authorizer.cj:286-296`）

```cangjie
// 条目级授权：必须条目 ID 相同
if (this.itemId != "") {
    return this.itemId == resource.itemId      // ← 命中即放行，跨主体也行
}
// 分类级授权：分类码相同（category=0 表示不限分类）
if (this.category != 0 && this.category != resource.category) {
    return false
}
// 主体级：必须同主体
return this.subjectId == resource.subjectId     // ← 分类匹配后仍然要求同主体
```

**关键事实**：`category` 分支匹配通过后**没有 return**，而是继续落到主体比较。
即 ——「分类授权」当前**只能在同一个主体内收窄**，设计稿写的「跨主体，按类目共享」**并不存在**。

#### 2.3 列表查询完全不看 `acl_grants`

`ItemRepo.list()` / `count()` 的 WHERE 只有一条归属条件：

```sql
AND subject_id IN (<accessible subject ids>)
```

而 `listAccessibleSubjectIds()` 的取值是：

```sql
SELECT DISTINCT id FROM arc_subjects
WHERE deleted_at IS NULL AND (owner_id = ? OR ? = ANY(custodian_ids))
```

**`acl_grants` 从未参与**。全站 12 处调用点（`items.cj:314`、`search.cj:81`、`export.cj:108`、`me.cj:142/418`、`fielddefs.cj:408`、`attachments.cj:475`、`permissionpreview.cj:100`、`itemtemplates.cj:215` …）都是同一口径。

**后果（已存在的 FR-ACL-008 缺口）**：被 `acl_grants` 显式授权的条目，**详情页打得开**（`findByIdRaw` 不过滤主体 + `Authorizer` 放行），但**列表里看不到**、**搜不到**、**导不出**。也就是说 FR-ACL-008 目前只完成了「详情可用」，列表侧是断的。

> 这一点直接决定了 §6 的推荐：不管选哪个粒度，**列表下推都必须做一遍**，这是绕不过去的地基工程。

#### 2.4 `custodian_ids` 有列、有读路径、**没有写入入口**

- 列：`arc_subjects.custodian_ids bigint[] NULL`
- 读：`subject.cj:64/85`、`user.cj:742` 都已支持 `? = ANY(custodian_ids)`
- 语义：`subject.cj:22` 注释明确「代管人（custodian）可读不可改」
- **写**：`SubjectRepo` 只有 `update()`（name/alias/relation/summary）与软删除，**全仓没有任何 API 或仓储方法写入 `custodian_ids`**

**后果**：「主体级共享」的数据结构与读路径现成可用，但缺一个「授予/撤销代管」的写入口。这是三档里成本最低的一档。

#### 2.5 三档粒度的真实成本表

| 粒度 | 表结构 | 判定语义 | 列表可见 | 缺什么 | 成本 |
| --- | --- | --- | --- | --- | --- |
| **主体** | ✅ `custodian_ids` 已有 | ✅ `ANY(custodian_ids)` 已通 | ✅ 现成 | **写入口**（授予/撤销 + 授权校验 + 审计） | **低** |
| **条目** | ✅ `item_id` 可空 | ✅ `itemId` 命中即放行 | ❌ 列表断裂 | **列表 UNION** + 授权 CRUD 收紧 | **中** |
| **分类（跨主体）** | ❌ `subject_id` NOT NULL | ❌ 仍要求同主体 | ❌ | 改表 + 改语义 + 改 SQL + 索引重建 | **高** |

### 3. 决策一 · §6 授权粒度

#### 方案 A：只做主体级

成员获得某主体的「代管（只读）」→ 该主体下**全部**条目可见。

- **优点**：完全复用现有列与读路径；没有新的可见性语义；`Authorizer` 一行都不用改
- **缺点**：不能「只给看学历，不给看健康」
- **代价**：约 3 个文件（`SubjectRepo.grantCustodian/revokeCustodian` + `FamilyRoutes` 授权端点 + 审计动作）

**风险点**：`custodian_ids` 的语义是「代管」，若未来某处把 custodian 当作可写角色，家庭只读共享会被动升级为可写。必须在授予时把「只读」写进设计约束，并在 `Authorizer` 侧确保 custodian 不携带写权限（当前 `subject.cj:22` 的注释保证，但**没有测试守着**）。

#### 方案 B：主体 + 条目（推荐）

- 主体级：按方案 A
- 条目级：复用 `acl_grants.item_id`，补**列表下推**（`subject_id IN (...) OR id IN (SELECT item_id FROM acl_grants WHERE ...)`)
- 分类级：**保持现状语义**，即「同主体内按分类收窄」。UI 文案明确写「该主体下的『教育经历』」，**不宣称跨主体**

- **优点**：
  - 覆盖两个真实诉求：「帮我妈管她的证件」（主体）与「只给孩子看这张房产证」（条目）
  - 分类级不需要改表，只是把已有多年的语义**如实写进文档**，不新增风险
  - 顺带修掉 FR-ACL-008 的列表断裂（否则条目级永远只是半个功能）
- **缺点**：列表下推是全局改动，见 §5 风险 R1
- **代价**：约 8~10 个文件

#### 方案 C：三档齐全（含跨主体分类）

- 需要：`subject_id` 改可空 → `covers()` 重写 → 列表 SQL 支持 category-only 分支 → 全站 12 处 `subject_id IN (...)` 逐一复核 NULL 语义 → 索引重建
- **优点**：设计稿 §6 完整落地，概念最干净
- **缺点**：
  - **动摇 FR-ACL-006「归属强制」这个全系统锚点**。`subject_id NOT NULL` 是「条目必属于某人」的物理保证，一旦可空，所有按归属过滤的查询都要回答「无主体的条目归谁」
  - 跨主体分类在家庭场景几乎无用：教育经历属于某一个人，不存在「全家共用教育经历」
  - 成本是方案 B 的 2~3 倍，收益接近 0
- **代价**：约 15~18 个文件 + 一次高风险迁移

#### 推荐

> **方案 B。**
>
> 判断依据是「归属强制」这条红线：`subject_id NOT NULL` 保证任何条目都能回答「这是谁的档案」。
> 为一个人群里几乎不存在的诉求（跨主体同类目共享）去松动这条约束，是典型的**用架构纯度换运维风险**。
> 分类授权的价值在「同一主体内缩小范围」（给家人看学历、不看健康），这个诉求方案 B 已经满足。

### 4. 决策二 · §13 R6 是否要「成员申请 → owner 审批」

#### 方案 A：不做审批流（推荐）

邀请链路保持 **owner/manager 主动发起 → 被邀请人输入邀请码接受**。

- **优点**：
  - 这是一条**方向正确**的链路：谁的数据谁决定给谁看，主动权在数据所有者手里
  - 邀请码本身就是凭据（8 位、短 TTL、一次性、可撤销、失败计数），安全性不依赖审批
  - 不引入新的通知/待办/状态机，不扩大攻击面
- **缺点**：owner 无法「收到申请后统一处理」；但家庭组通常 ≤ 8 人，不构成痛点

#### 方案 B：只做「邀请需二次确认」

邀请创建后进入 pending，owner 需在同一会话内确认才下发 code。

- **优点**：听起来更严谨
- **缺点**：**逻辑倒置** —— 发起邀请的人就是 owner 本人，等于「我确认我自己的操作」，纯增摩擦
- **结论**：不推荐，属于形式主义安全

#### 方案 C：完整「申请单」模型

任何人都可以向任意组提交入组申请，owner 审批通过后成为成员。

- **优点**：适合「陌生人加入公开协作组」的机构场景
- **缺点（关键）**：
  - **开出新的骚扰与枚举通道**：任意账号可向任意组投递申请，owner 的通知箱会被塞满；申请本身也变成了「这个组存在」的探测信号 —— 与设计稿 §3 的「No Enumeration」原则直接冲突
  - 需要新增：`fam_join_requests` 表、状态机（pending/approved/rejected/expired）、通知模板、审批页、频率限制、批量拒绝
  - 家庭场景没有这个诉求：家里人是你认识的，你直接发码给他
- **代价**：约 6~8 个额外文件，且把「一次确认」变成「两次确认 + 一个可被滥用的入口」

#### 推荐

> **方案 A：不做。**
>
> 真正的安全诉求不是「多一道审批」，而是**事后可追溯 + 随时可撤销** —— 这两点由
> F1 的入组审计、F4 的 10 个审计动作码、以及「移除成员 = 同时撤销全部授权并登出会话」共同覆盖。
> 审批流解决的是「我不信任发起人」，而这里发起人就是数据所有者本人。

### 5. 决策三 · §14 分批

#### 方案 A：保持原 4 批（F1 组/成员/邀请 → F2 授权+下推 → F3 前端 → F4 审计）

- **问题**：F1 结束时成员**零可见** —— 能拉人进组，但进来什么也看不到。这不是「阶段性成果」，是**不可验收的半成品**：既没法演示，也没法让用户判断方向对不对
- F2 的列表下推又必须在 F1 之后，两批之间存在强耦合的空窗期

#### 方案 B：3 批，每批都收在可演示闭环（推荐）

| 批次 | 内容 | 结束时能演示什么 | 文件量 |
| --- | --- | --- | --- |
| **B1** 最小可用闭环 | 迁移 019（`fam_groups`/`fam_members`/`fam_invites` + `acl_grants.group_id`）<br>`FamGroupRepo`/`FamMemberRepo`/`FamInviteRepo`<br>`FamilyService`（建组/邀请/接受/移除）<br>`SubjectRepo.grantCustodian/revokeCustodian`<br>`FamilyRoutes`（组 + 成员 + 邀请 + 主体级授权）<br>前端 `/family` 列表 + 组详情 + 邀请面板 | **拉人进组 → 他能看到我授权的整个主体** | 8~10 |
| **B2** 精细授权 | `ItemRepo.list/count` 加授权 UNION（**全局风险点**）<br>授权 CRUD 收紧（条目级 + 分类收窄）<br>前端授权面板（选成员 → 选范围 → 选有效期） | **只把某一张证给孩子看** | 6~8 |
| **B3** 收口 | 10 个审计动作码落链<br>§12.3 安全用例全跑通<br>`docs/14` 按本文结论定稿回写 | 可交付、可举证 | 3~4 |

- **优点**：B1 结束就是一个能演给用户看的东西；B2 的价值点（精细授权）单独一批，失败也不会拖垮 B1
- **缺点**：B1 略胖（后端 + 前端同时上）

#### 方案 C：5 批（把前端拆出去）

B1 后端组/邀请 → B2 后端主体级授权 → B3 前端组/邀请 → B4 后端+前端条目级 → B5 收口

- **优点**：每批更小
- **缺点**：B1/B2 结束时**用户看不到任何界面**，无法验收；前端与后端来回切，上下文成本高

#### 推荐

> **方案 B：3 批。**
>
> 依据是「每批必须能被演示」这一条：用户判断方向对不对的唯一方式是**看到东西**。
> 原 4 批里 F1 与 F2 之间存在「能拉人但什么也看不到」的空窗，是最容易做完发现方向错了的结构。

#### 批次内的硬约束（沿用设计稿 §14）

每批都必须通过：
- `bash scripts/build.sh` → 0 error
- `npm run build` → 0 error
- `bash scripts/test.sh` → 0 fail
- 新增对应单测；安全用例（§12.3）在 B3 前全部跑通

### 6. 全局风险：B2 的列表下推会同时改变 6 个入口的语义

`ItemRepo.list/count` 是**列表、搜索、导出、批量编辑、权限预览、附件面板**的共同底层。一旦把「授权范围」并入 WHERE：

| 入口 | 现状 | 加入授权后必须回答的问题 |
| --- | --- | --- |
| 档案列表 `GET /api/items` | 只按主体 | 被授权单条目是否出现在「全部主体」视图下？ |
| 搜索 `GET /api/search` | 只按主体 | 搜索结果是否包含授权条目？来源标签怎么标？ |
| 导出 | 只按主体 | 导出「我的全部档案」是否会把别人授权给我的条目打包带走？ |
| 批量编辑 | 只按主体且**要求写权限** | 授权是只读的，必须确认批量写仍然被拒 |
| 权限预览 `countVisible` | 只按主体 | 预览数字会变 —— 这其实是**修正**（原先漏算授权） |
| 附件面板 | 只按主体 | 授权条目的附件能不能下载？（应能，只读） |

**结论**：B2 不是「加个 OR 条件」，而是**一次语义统一**。必须：
1. 抽一个 `AccessScope`（主体集合 + 授权条目集合）作为所有入口的唯一入参，禁止各路由自己拼；
2. 补 1 条跨入口回归用例：同一条授权在 6 个入口的可见性判定**完全一致**；
3. 导出侧单独决策：默认**不把授权条目打进「我的档案」导出包**（避免用户无意识地把别人的数据导出传播），需要在导出页显式勾选。
