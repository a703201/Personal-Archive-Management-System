## 一、提炼通用开发框架

### 现状
AMS 内部已沉淀一批高质量、可复用的能力（分散在各包）：
- **密码学**：`ams-crypto`（SM3 / HMAC-SM3 / SM4-CBC·CTR / PBKDF2-HMAC-SM3 / 盲索引）
- **鉴权**：`ams-security`（认证、TOTP、限流）+ `ams-app.authz`（对象级 ACL guard）
- **审计**：哈希链（`ams-app.audit`）
- **导入**：模板映射 + CSV 框架（`ams-app.importer` + `ams-api.routes.import*`）
- **存储 / 检索**：`ams-storage` / `ams-core.search`

这些能力目前**强耦合于 AMS 业务语义**（如 `arc_*` 表、`Subject`/`Item` 领域对象），
外部项目无法直接引用。

### 候选方案

**方案 A：独立框架库（推荐）**
- 把与业务无关的部分抽成独立 Cangjie 包 / 仓（如 `cangjie-kit-crypto`、`cangjie-kit-authz`），
  通过 cjpm 依赖引入 AMS 与其他项目。
- 优点：真正的跨项目复用、可独立版本化与测试、契合「信创自主可控」叙事。
- 代价：需定义稳定 API 边界，初期要把业务耦合点（表名、领域类型）参数化/回调化。
- 工作量：中（约 2~3 周，先 crypto 与 authz 两块试点）。

**方案 B：仓库内 shared 模块 + 文档化**
- 在 AMS 仓内新开 `packages/ams-framework`（或 `shared/`），仅做物理隔离与接口收敛，
  不跨仓发布。
- 优点：零发布链路成本，改动可控。
- 代价：复用范围限于本仓，外部项目仍需 copy。
- 工作量：小（约 3~5 天）。

**方案 C：脚手架 / 代码生成器**
- 提供 CLI，从模板生成「带鉴权 + 审计 + 加密 + 限流」的新服务骨架。
- 优点：新项目起步最快。
- 代价：生成器的维护成本随模板膨胀，且与 Cangjie 生态成熟度强相关。
- 工作量：大（需先有稳定的框架层，否则生成的是「坏模板」）。

> 推荐：**先 A 试点（crypto、authz 两块）+ B 作为过渡**。C 待 A 稳定后考虑。

## 二、SaaS / 微服务化

### 现状
- **单体单进程**：`ams-server` 一个进程同时提供 `/api/*` 与前端 SPA（`packages/ams-api/src/server/static.cj`）。
- **单库单租户**：openGauss 一个库；权限模型有 `org_admin` / `owner` 等角色，
  但**没有租户隔离层**（无 `tenant_id`、无跨租户数据边界）。
- **部署**：物理机发布包（`scripts/package.sh`）或容器（本批次新增），均为单实例。

### 候选方案

**方案 A：多租户单体（推荐起步）**
- 引入 `tenant_id` 到核心表，在仓储/中间件层做行级隔离；共享一个 DB 与进程。
- 优点：改动最小、运维简单、不引入分布式复杂度，即可对外以「SaaS 账号」交付。
- 代价：单库存在资源争用上限，超大客户需后续拆分。
- 工作量：中（数据迁移 + 隔离中间件 + 测试，约 2~4 周）。

**方案 B：模块化单体（为微服务铺路）**
- 在单体内按业务边界划清模块（认证 / 档案 / 导入 / 检索 / 审计），模块间仅通过
  明确接口通信；进程仍单一，但接口已「可抽取」。
- 优点：在不引入运维复杂度的前提下完成边界治理，是 C 的前置步骤。
- 代价：需要一次较大的内部重构（理清 `ams.api` 对 `ams.app` 的隐性依赖）。
- 工作量：大（约 4~6 周）。

**方案 C：完整微服务**
- 拆分为 `auth-service` / `archive-service` / `import-service` / `search-service` 等，
  各自独立进程与（可选）独立库，前置 API 网关 + 消息总线。
- 优点：独立伸缩、故障隔离、团队并行。
- 代价：分布式事务、服务发现、链路追踪、运维体系全面升级；以当前团队/阶段
  **性价比低**，且 Cangjie 微服务生态尚不成熟。
- 工作量：很大（需先完成 B，再加网关与运维，约 2~3 个月）。

> 推荐：**A（多租户单体）作为第一阶段**，B 作为「何时拆微服务」的成熟度门槛
> （当单实例资源或团队规模触顶时再走 C）。

## 三、决策结果（已拍板 · 2026-10-29）

| 决策点 | 结论 | 说明 |
|--------|------|------|
| 通用框架形态 | **A 独立框架库** | 先把 `ams-crypto`、`ams-security.authz` 等业务无关能力抽成独立可发布包（cjpm 跨项目引入），以 crypto + authz 两块试点 |
| SaaS 第一步 | **A 多租户单体** | 引入 `tenant_id` 行级隔离，共享单库单进程；不引入分布式复杂度 |
| 试点范围（框架） | crypto + authz 先行 | 其余模块（审计 / 导入 / 检索）待试点稳定后纳入 |
| 是否现在开工 | 分批执行（阶段 1/2 已落地，阶段 3 待办） | 见下方分阶段计划，每阶段独立可验证、可回滚 |

- **阶段 1 · 数据层隔离 — ✅ 已完成（2026-10-29）**

  - **隔离策略（传递性隔离 + 显式 tenant_id）**：因 stdx **并发**处理请求（`server.cj` 用 `ParamDistributor` 注册到 stdx `ServerBuilder`，无单请求串行保证），无法用品圆线程级 ambient context，采用「传递性 + 显式」混合：
    - `UserRepo.listAccessibleSubjectIds` / `listOwnedSubjectIds` 内部按 `tenantOf(userId)` 推导租户并过滤 `arc_subjects.tenant_id`；几乎所有 item 查询都按 `subjectIds` 过滤，租户隔离由此**传递性**覆盖（调用方零改动）。
    - 不按 subjectIds 过滤的写路径 `ItemRepo.create` / `cloneItem` 显式带 `tenant_id`（写入 + clone 复制并校验同租户）。
    - **`ItemRepo.findByIdRaw` 保持租户无关**：它是鉴权 guard 通过后按 id 取数据的「后鉴权」加载点，隔离已由 guard 的 tenant-scoped subjectIds 保证；若此处加 `tenant_id` 会破坏共享链接 / 被授权用户的 FR-ACL-008 通路。
