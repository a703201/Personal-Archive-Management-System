# AMS · 二次开发与衍生版本接入指南

> 本文面向**希望基于 AMS 做二次开发或衍生版本**的开发者。
> - 仅终端部署使用：见 `docs/09-部署与发布指南.md`。
> - 仅想把 AMS 的纯逻辑能力嵌入自己的程序：见 `packages/ams-kit/README.md`（框架分发）。

## 1. 两种集成路径

### 路径 A：整库二次开发（fork / 直接扩展）

适用：要在 AMS 之上叠加自有业务（新的档案类型、审批流、外部系统集成等），复用完整后端与 Web 前端。

- 直接 clone 本仓，修改业务层 `ams.app` / `ams.data` / `ams.api`。
- 分层单向依赖：`kernel→crypto→storage→core→data→security→app→api→server`；**`ams.app` 不得 import `ams.api`**。
- 复用全部构建 / 测试门禁与发布流程（见 §3、§4、§5）。
- 代价：跟随上游需 rebase；业务包改动量大。

### 路径 B：仅复用 ams-kit 框架纯逻辑（衍生独立项目）

适用：只想用 AMS 沉淀的**通用纯逻辑**——国密密码学、审计哈希链、中文检索分词 / 掩码 / 高亮、CSV 导入模板内核——不引入任何档案业务。

- 不 clone 业务代码，只下载 `ams-kit-<KIT_VERSION>-windows-x86_64.zip`（GitHub Release 资产，由 CI 随发版自动上传）。
- 按 `packages/ams-kit/README.md` 的「接入方式」编译链接。**本包不是 cjpm 包，勿执行 `cjpm build` / `cjpm publish`**。
- 优点：与 AMS 业务彻底解耦，可独立演进；缺点：不随 AMS 业务层更新。

> 选择依据：要「带业务的能力」走路径 A；要「纯逻辑积木」走路径 B。两者许可一致（Apache-2.0）。

## 2. 开发环境

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| 仓颉 SDK（cjc） | 1.2.0 | 与 `cjc-version` 一致；CI 经 `scripts/ci/setup-toolchain.sh` 自举准备 |
| stdx | 1.2.0.1 | 同版本 |
| Node.js | 22 | 前端 `web/` 构建与测试 |
| openGauss / 兼容 DB | — | 运行态；CI 无 DB 时打包校验识别为「数据库不可用，非打包问题」 |

- 本地构建（Windows）：`bash scripts/build.sh`；Linux 容器：`bash deploy/scripts/build-linux-docker.sh`。
- **CI 用 cjpm，本地 Windows 不用 cjpm**（cjpm 1.0.5 在 Windows 触发堆损坏，统一走 `bash scripts/build.sh`）。

## 3. 质量门禁（三件套，缺一无意义）

1. `bash scripts/build.sh` —— 0 error 编译后端。
2. `bash scripts/test.sh` —— 全量单测（约 14 分钟，建议后台；缺构建产物时 test.sh 会自动先 build）。
3. `cd web && npm run build` —— 前端 EXIT=0。

版本一致性：`scripts/ci/check-consistency.py` 校验 `web/package.json` 与 `main.cj` 的版本号是否一致。

## 4. 版本策略

AMS 有**两条相互独立的版本序列**，请勿混淆：

| 序列 | 唯一来源 | 当前 | 用途 |
| --- | --- | --- | --- |
| 产品版本 | `web/package.json` 的 `version`（并同步 `main.cj` / 部署镜像 tag） | 1.3.1 | 整个 AMS 的发布版本，决定二进制发布包名 `ams-release-<v>-windows-x86_64.zip` |
| 框架版本 | `packages/ams-kit/src/kit.cj` 的 `KIT_VERSION` | 0.1.0-alpha | 仅 ams-kit 框架静态库包，决定 `ams-kit-<KIT_VERSION>-<platform>.zip` |

- **语义化版本（SemVer）**：产品版本用 `MAJOR.MINOR.PATCH`。MINOR 表示新功能模块 / 安全加固，PATCH 为缺陷修复。
- **破坏性变更必须显式标注**：对外 API（见 `docs/14-对外API规范-OpenAPI.yaml`）变更若破坏兼容，需 bump MAJOR 并在 CHANGELOG 标注，否则 CI 契约门禁失败（`docs/04` §7.8）。
- 对外 API 版本化路径 `/api/v1`；废弃接口用 `Deprecation` / `Sunset` 响应头 + 监控调用量后下线（`docs/04` §7.7）。
- 升级上游：优先 rebase 而非制造大冲突 merge；业务包改动请保持分层单向依赖不被反向 import 破坏。

## 5. 发布与分发

- **本地脚本**：`bash scripts/release.sh --version <v>`（不依赖 CI runner）。
- **打 tag 触发 CI**：
  ```bash
  git tag -a v<v> -m "AMS <v>"
  git push origin v<v>
  ```
  → `release.yml` 自动编译、单测、打包，**同时产出并上传二进制包与 ams-kit 框架包**；Release notes 自动取自 `CHANGELOG.md` 的 `[<v>]` 段落。
- 多远程：推送 `origin`(GitHub) / `gitea` / `gitcode_origin` 三路。

## 6. 许可与合规

- 许可 **Apache-2.0**（取第 3 条明示专利授权）。`LICENSE` 必须随发布包 / 衍生包分发；`scripts/package.sh` 与 `scripts/package-kit.sh` 均强制校验，缺失即拒绝出包。
- 衍生版本须保留版权与许可声明，不得移除 LICENSE。
- 国密能力 ≠ 商用密码产品认证；强监管场景需另行送检（见 `packages/ams-kit/README.md` §6、`docs/03`）。
