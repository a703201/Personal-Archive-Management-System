# AMS · 二次开发与衍生版本接入指南

> 本文面向**希望基于 AMS 做二次开发或衍生版本**的开发者。
> - 仅终端部署使用：见 `docs/09-部署与发布指南.md`。
> - 仅想把 AMS 的纯逻辑能力嵌入自己的程序：见 `packages/ams-kit/README.md`（框架分发）。

## 1. 两种集成路径

### 路径 A：整库二次开发（fork / 直接扩展）

适用：要在 AMS 之上叠加自有业务（新的档案类型、审批流、外部系统集成等），复用完整后端与 Web 前端。

- 直接 clone 本仓，修改业务层 `ams.app` / `ams.data` / `ams.api`。
- 分层单向依赖：`kernel→crypto→storage→core→data→security→app→api→server`；**`ams.app` 不得 import `ams.api`**。
- 复用全部构建 / 测试门禁与发布流程（见 §3、§4、§5）。
- 代价：跟随上游需 rebase；业务包改动量大。

### 路径 B：仅复用 ams-kit 框架纯逻辑（衍生独立项目）

适用：只想用 AMS 沉淀的**通用纯逻辑**——国密密码学、审计哈希链、中文检索分词 / 掩码 / 高亮、CSV 导入模板内核——不引入任何档案业务。

- 不 clone 业务代码，只下载 `ams-kit-<KIT_VERSION>-windows-x86_64.zip`（GitHub Release 资产，由 CI 随发版自动上传）。
- 按 `packages/ams-kit/README.md` 的「接入方式」编译链接。**本包不是 cjpm 包，勿执行 `cjpm build` / `cjpm publish`**。
- 优点：与 AMS 业务彻底解耦，可独立演进；缺点：不随 AMS 业务层更新。

> 选择依据：要「带业务的能力」走路径 A；要「纯逻辑积木」走路径 B。两者许可一致（Apache-2.0）。

## 2. 开发环境

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| 仓颉 SDK（cjc） | 1.2.0 | 与 `cjc-version` 一致；CI 经 `scripts/ci/setup-toolchain.sh` 自举准备 |
| stdx | 1.2.0.1 | 同版本 |
| Node.js | 22 | 前端 `web/` 构建与测试 |
| openGauss / 兼容 DB | — | 运行态；CI 无 DB 时打包校验识别为「数据库不可用，非打包问题」 |

- 本地构建（Windows）：`bash scripts/build.sh`；Linux 容器：`bash deploy/scripts/build-linux-docker.sh`。
- **CI 用 cjpm，本地 Windows 不用 cjpm**（cjpm 1.0.5 在 Windows 触发堆损坏，统一走 `bash scripts/build.sh`）。

## 3. 质量门禁（三件套，缺一无意义）

1. `bash scripts/build.sh` —— 0 error 编译后端。
2. `bash scripts/test.sh` —— 全量单测（约 14 分钟，建议后台；缺构建产物时 test.sh 会自动先 build）。
3. `cd web && npm run build` —— 前端 EXIT=0。
4. `cd web && npm test` —— 前端单测（vitest，含 AI 关闭态断言；1.4.0 新增）。

版本一致性：`scripts/ci/check-consistency.py` 校验 `web/package.json` 与 `main.cj` 的版本号、OpenAPI operation 覆盖（1.4.0 为 215/215）、i18n 三语键数一致。

## 4. 版本策略

AMS 有**两条相互独立的版本序列**，请勿混淆：

| 序列 | 唯一来源 | 当前 | 用途 |
| --- | --- | --- | --- |
| 产品版本 | `web/package.json` 的 `version`（并同步 `main.cj` / 部署镜像 tag） | 1.4.0 | 整个 AMS 的发布版本，决定二进制发布包名 `ams-release-<v>-windows-x86_64.zip` |
| 框架版本 | `packages/ams-kit/src/kit.cj` 的 `KIT_VERSION` | 0.1.0-alpha | 仅 ams-kit 框架静态库包，决定 `ams-kit-<KIT_VERSION>-<platform>.zip` |

- **语义化版本（SemVer）**：产品版本用 `MAJOR.MINOR.PATCH`。MINOR 表示新功能模块 / 安全加固，PATCH 为缺陷修复。
- **破坏性变更必须显式标注**：对外 API（见 `docs/14-对外API规范-OpenAPI.yaml`）变更若破坏兼容，需 bump MAJOR 并在 CHANGELOG 标注，否则 CI 契约门禁失败（`docs/04` §7.8）。
- 对外 API 版本化路径 `/api/v1`；废弃接口用 `Deprecation` / `Sunset` 响应头 + 监控调用量后下线（`docs/04` §7.7）。
- 升级上游：优先 rebase 而非制造大冲突 merge；业务包改动请保持分层单向依赖不被反向 import 破坏。

## 5. 发布与分发

- **本地脚本**：`bash scripts/release.sh --version <v>`（不依赖 CI runner）。
- **打 tag 触发 CI**：
  ```bash
  git tag -a v<v> -m "AMS <v>"
  git push origin v<v>
  ```
  → `release.yml` 自动编译、单测、打包，**同时产出并上传二进制包与 ams-kit 框架包**；Release notes 自动取自 `CHANGELOG.md` 的 `[<v>]` 段落。
- 多远程：推送 `origin`(GitHub) / `gitea` / `gitcode_origin` 三路。

## 6. 许可与合规

- 许可 **Apache-2.0**（取第 3 条明示专利授权）。`LICENSE` 必须随发布包 / 衍生包分发；`scripts/package.sh` 与 `scripts/package-kit.sh` 均强制校验，缺失即拒绝出包。
- 衍生版本须保留版权与许可声明，不得移除 LICENSE。
- 国密能力 ≠ 商用密码产品认证；强监管场景需另行送检（见 `packages/ams-kit/README.md` §6、`docs/03`）。

## 7. AI 能力接入（1.4.0 新增）

AMS 1.4.0 在分层体系中新增一个**基础设施层包 `ams-ai`**，为四能力域（V 视觉识别 / S 档案总结 / Q 自然语言查询 / A 智能建议）提供统一的模型接入底座。完整设计见 `docs/20-AI视觉识别与模型接入设计.md`，本节只讲二次开发的扩展点。

### 7.1 包定位与分层

```
kernel → crypto → storage → core → data → security → app → api → server
                         ↘ ams-ai ↗（基础设施层，不依赖 core/data）
                              ↓
                   ams-app/src/ai/*（领域翻译，唯一调用方）
```

- `ams-ai`（`packages/ams-ai/src/`）：provider 抽象、OpenAI 兼容出站客户端、五层提示词、容错 JSON `AiJson`、能力发现、审计与回退；**不 import core/data**，不监听端口（纯出站 HTTP）。
- `ams-app/src/ai/`：领域翻译层，`AiService` / `AiRecognizeService` / `AiIntakeService` / `AiQueryService` / `AiTextService` / `AiAdminService`，是 `ams-ai` 的唯一调用方。
- **禁止**绕过 `ams-app` 从 `ams-api` 直接调用 `ams-ai`；跨层 import 数量由一致性门禁锁定（基线 26，不得增长）。

### 7.2 新增的 9 条 AI API

均在 `packages/ams-api/src/routes/ai.cj` 注册，已写入 `docs/14` OpenAPI（215/215 覆盖）。

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/ai/capabilities` | `archive:read:own` | 能力发现（前端门控唯一数据源） |
| PUT | `/api/me/ai-preference` | `archive:read:own` | 用户 opt-out 偏好（存服务端、跨设备） |
| POST | `/api/attachments/:id/ai-parse` | `archive:read:own` | V5 附件解析 → 字段候选（来源/置信度） |
| POST | `/api/search/ask` | `archive:read:own` | Q 域自然语言 → 搜索条件 + grounded 回答 |
| POST | `/api/summary/items/:id` | `archive:read:own` | S 域摘要候选（不落库） |
| POST | `/api/advice/items/:id` | `archive:read:own` | A 域建议候选（不落库） |
| GET | `/api/admin/ai/config` | `system:admin` | 读配置（密钥脱敏为 `***`） |
| PUT | `/api/admin/ai/config` | `system:admin` | 写 provider / 端点 / 密钥 / 开关 |
| POST | `/api/admin/ai/test` | `system:admin` | 连通性测试（只回 ok/reason） |

### 7.3 扩展一个 provider 的步骤

1. 在 `packages/ams-ai/src/provider.cj` 的 `AiProviderKind` 加枚举成员，`providerName()` 补名称。
2. 若是 OpenAI 兼容协议（绝大多数在线服务 + Ollama/LM Studio 的 `/v1`），无需新客户端——`OpenAIClient` 复用即可；只需在配置里指定 `base_url` / 模型名 / 鉴权头。
3. 若是非兼容原生协议（如 Ollama `/api/chat`），在 `client.cj` 增适配器，把请求/响应归一化到 `AiChatResponse`。
4. 更新 `web/src/components/AiConfigPanel.vue` 的 `PROVIDERS` 下拉与三语 catalog（**三语必须同步**，否则 en/fr 回退中文）。
5. 文档同步：`docs/20` §7 接口表 + §14 变更记录、`docs/14` OpenAPI（若改契约）。

> 视觉能力差异：`bbox`/`snippet` 并非所有 provider 都支持，`attachmentId`+`page` 由 AMS 侧兜底（docs/20 §7.5）；前端不得假设所有模型都能给坐标。

### 7.4 前端接入点

- `web/src/composables/useAiCapabilities.ts`：**能力发现唯一数据源**，禁止页面自行判断开关组合。导出的 `isAiEnabled` / `isDomainEnabled` 纯函数供 vitest 直接断言。
- `web/src/components/AiFeatureGate.vue`：按 `domain` 整块 `v-if` 移除 AI 入口（不是置灰），节点打 `data-ai-feature` 供无头 Chrome + CDP 断言。
- `web/src/components/AiIntakePanel.vue` / `AiAskPanel.vue` / `AiInsightPanel.vue`：V/Q/S/A 三域 UI；`AiConfigPanel.vue`：管理员配置卡（**关闭态仅留一个启用总开关**，其余项与测试按钮 `v-if` 隐藏）。
- 用户侧唯一恢复开关在 `ProfileView`；系统侧恢复开关在 `SystemView` 的 AI 配置卡（OQ13 已定稿）。
- i18n 词条只在 `web/src/i18n/catalog.*` 定义，且 `t()` 不插值——动态文案用 `{name}` 占位符 + 调用点 `.replace()`。

### 7.5 内置离线模型 FFI 的接线位置（待资产）

方案已定（docs/20 §7.7）：PP-OCRv5（≈22MB，已有生产资产）+ Qwen2.5-0.5B Q4（≈350MB）。二次开发若要接入真实权重：

- C 侧：`packages/ams-ai/native/llama/llama_bridge.c`（`AMS_HAS_LLAMA` 宏切换桩/真推理骨架）+ `llama_bridge_stub.c`（零依赖桩）。
- 仓颉侧：`packages/ams-ai/src/localmodel.cj` 的 `LocalTextModel.probe()` 当前**恒回退**（未接线），接入真 FFI 后需返回可用状态；`ams-app/src/ai/aiservice.cj` 的 `buildProviders()` 会据此决定是否加入内置 provider。
- 注意：`LocalBuiltin` 走的是进程内推理，**不是 HTTP**；`AiGateway` 当前所有 provider 都走 `OpenAIClient`，真接线时需为 `LocalBuiltin` 增加独立 `LocalClient` 分支。当前 `probe()` 恒 false，不会走到该分支，故门禁不受影响。
- 模型权重不进 git，随镜像或挂载卷分发。

### 7.6 联调脚本（Ollama 就绪后）

```bash
# 1) 探测 Ollama 是否就绪、列出已加载模型、给出配置页应填值（只读）
bash scripts/dev/ollama-smoke.sh

# 2) 配好 AMS 后，对 9 条 AI 接口做可达/鉴权/契约冒烟（不写数据）
AMS_TOKEN=<token> bash scripts/dev/ai-live-check.sh
# 或： AMS_USER=admin AMS_PASS=xxx bash scripts/dev/ai-live-check.sh
```

两个脚本明确区分「AMS 路由可达」「provider 未就绪降级」「真推理」三层，Ollama 未起时不会误判为 AMS 故障。

**关键：端点要按 AMS 运行形态填**（脚本会自动识别并给出正确值）：

| AMS 形态 | Ollama 端点（配置页填） | 说明 |
| --- | --- | --- |
| 本地二进制直接跑 | `http://127.0.0.1:11434/v1` | 同机回环 |
| Docker 容器（`ams-server`） | `http://host.docker.internal:11434/v1` | 容器内 `127.0.0.1` 指向容器自己，**连不到宿主机 Ollama**；Docker Desktop 默认注入该 DNS，已实测容器内 curl 返回 200 |

若容器版 `host.docker.internal` 不通，给 `ams-server` 加 `extra_hosts: ["host.docker.internal:host-gateway"]` 后重建容器。

**Windows Ollama 启动坑**：装完后若只有托盘 `ollama app.exe`、11434 无响应（`ollama list` 报 `timed out waiting for server to start`），是 GPU 探测卡住。用 CPU 模式启动可绕过：

```bash
export OLLAMA_VULKAN=false OLLAMA_LLM_LIBRARY=cpu
"/d/Program Files/Ollama/ollama.exe" serve    # 路径按实际安装位置调整
```
