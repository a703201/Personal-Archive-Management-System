# 09 · 部署与发布指南

> 适用范围：AMS 后端服务（`ams-server`）的打包、发布、部署与运维。
> 交付物结构依据 [02-架构设计说明](02-架构设计说明.md) §7.3。

---

## 1. 两种发布方式

### 方式 A：本地脚本发布（不依赖 CI runner）★ 推荐先用这个

```bash
# 1. 提交并推送代码
git add -A && git commit -m "feat: xxx" && git push origin develop

# 2. 发布（自动：打包 → 推 tag → 建 Release → 上传资产）
export GITHUB_TOKEN=ghp_xxx
bash scripts/release.sh --version 0.2.0
```

脚本会依次完成：

1. 检查工作区是否干净（有改动会拒绝并列出）
2. 打包（`scripts/package.sh`）
3. 打 tag 并推送
4. 调 GitHub REST API 创建 Release（复用 `CHANGELOG.md` 对应段落作为说明）
5. 上传 zip 资产

> **为什么不用 `gh` CLI**：本机未安装 gh，脚本直接用 `curl` 调 REST API，
> 少一个依赖。装了 gh 也可用 `bash scripts/package.sh && gh release create ...`，效果等价。

### 方式 B：打 tag 触发 GitHub Actions

```bash
git tag -a v0.2.0 -m "AMS 0.2.0"
git push origin v0.2.0
```

`.github/workflows/release.yml` 会自动构建、测试、打包、校验并上传资产。

> ⚠️ 方式 B 需要**自托管 Windows runner**（已装仓颉 SDK 1.2.0 的机器）。
> 详见 §5。

## 2. 交付物结构

```
ams-release-<version>-windows-x86_64/
├── bin/
│   ├── ams-server.exe          主程序
│   ├── libstdx.*.dll           stdx 运行时（44 个）
│   ├── libcangjie-*.dll        仓颉运行时
│   ├── libgcc_s_seh-1.dll      MinGW 运行库 ★ 缺了启动即崩
│   ├── libwinpthread-1.dll     MinGW 运行库 ★
│   └── libpcre2-8.dll          MinGW 运行库 ★
├── config/
│   └── application.env         配置模板（**不含任何密钥**）
├── scripts/
│   ├── start.cmd               启动（Windows）
│   └── healthcheck.cmd         健康检查（Windows）
├── docs/
│   ├── README.md
│   └── 08-SM4方案变更说明.md
├── DEPLOY.md                   部署说明
├── VERSION
└── CHECKSUMS.sha256            逐文件校验和
```

> ### ⚠️ 运行时必须随包分发
>
> **漏发 DLL 是部署期最常见的问题**，表现为启动瞬间报：
> ```
> error while loading shared libraries: cannot open shared object file
> ```
>
> 三个来源都要带上：
> 1. **stdx 动态库**（`libstdx.*.dll`）—— 仓颉扩展库
> 2. **仓颉运行时**（`libcangjie-*.dll`）—— 语言运行时
> 3. **MinGW 运行库**（`libgcc_s_seh-1.dll` / `libwinpthread-1.dll` / `libpcre2-8.dll`）
>    —— ⚠️ **SDK 1.2.0 的 Windows 包本身不含这三个文件**，需从 Git for Windows
>    或 SDK 的 `tools/cangjie/bin/` 补齐
>
> `scripts/package.sh` 已内置校验：缺任一必需 DLL 会**直接失败**，不会产出坏包。

## 3. 部署步骤

### 3.1 解压与配置

```bash
unzip ams-release-0.2.0-windows-x86_64.zip
cd ams-release-0.2.0-windows-x86_64

# 复制配置模板并填写
cp config/application.env config/application.env.local
```

必填项：

| 变量 | 说明 | 生成方式 |
| --- | --- | --- |
| `AMS_TOKEN_SECRET` | 令牌签名密钥，**≥ 32 字节** | `openssl rand -base64 48` |
| `AMS_DB_PASSWORD` | 数据库口令 | — |
| `AMS_DB_HOST` / `AMS_DB_PORT` / `AMS_DB_NAME` / `AMS_DB_USER` | 数据库连接 | — |

> ⚠️ **数据库口令不要做 percent-encoding**。
> 驱动（opengauss-driver）**不解码** `%XX`，编码后会导致认证失败：
> `SqlException: Invalid username/password,login denied. (SQLSTATE 28P01)`。
> 口令含 `@` 等保留字符时**原样填入**即可。

> ⚠️ **不要把密钥写进 `application.env` 后提交到仓库**。
> 该文件在 `.gitignore` 中；生产环境建议用容器 secret / systemd EnvironmentFile。

### 3.2 启动

```bash
# Linux / macOS
set -a; . ./config/application.env; set +a
scripts/start.sh

# Windows
set AMS_TOKEN_SECRET=...
scripts\start.cmd
```

未设置 `AMS_TOKEN_SECRET` 时脚本会**拒绝启动**（防止误用代码里的开发默认值）。

### 3.3 健康检查

```bash
scripts/healthcheck.sh
# → {"code":"OK","message":"success","data":{"status":"ok"},"requestId":"..."}
```

## 4. 运维

### 4.1 以 Windows 服务运行

```powershell
# 用 NSSM 或 WinSW 包装
nssm install AMS "E:\ams\bin\ams-server.exe"
nssm set AMS AppEnvironmentExtra AMS_TOKEN_SECRET=xxx AMS_DB_PASSWORD=yyy
nssm set AMS AppDirectory E:\ams
nssm start AMS
```

### 4.2 以 Linux 服务运行

```ini
# /etc/systemd/system/ams.service
[Unit]
Description=AMS Server
After=network.target

[Service]
Type=simple
User=ams
WorkingDirectory=/opt/ams
EnvironmentFile=/opt/ams/config/application.env
ExecStart=/opt/ams/bin/ams-server
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 4.3 关键环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AMS_HTTP_HOST` | `127.0.0.1` | 监听地址。容器/反向代理场景设为 `0.0.0.0` |
| `AMS_HTTP_PORT` | `8080` | 监听端口 |
| `AMS_TOKEN_SECRET` | （无默认，必填） | 令牌签名密钥，≥ 32 字节 |
| `AMS_DB_*` | 见模板 | 数据库连接 |
| `AMS_LOG_LEVEL` | `info` | 日志级别 |

## 5. CI / Release 流水线

### 5.1 工作流

| 文件 | 触发 | 作用 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push / PR / 手动 | 工具链 → 构建 → 测试 → 打包 → **校验发布包可运行** |
| `.github/workflows/release.yml` | 推 `v*` tag / 手动 | 工具链 → 构建 → 测试 → 打包 → 校验 → **上传 GitHub Release** |

两个工作流都会执行 `scripts/ci/verify-package.sh`，
它会**真实启动**打包出的程序并检查运行时是否齐全（不是只看文件在不在）。

### 5.2 工具链准备

`scripts/ci/setup-toolchain.sh` 按优先级取工具链：

1. **已有 SDK**（`CANGJIE_HOME` 指向有效目录）→ 零下载
2. **仓库内副本** `tools/cangjie/`
3. **缓存** `~/.cache/ams-toolchain/`
4. **下载**（需 `CANGJIE_SDK_URL`）

stdx 从 gitcode 官方 release 下载（地址已内置，实测可用）：
`https://gitcode.com/Cangjie/cangjie_stdx/releases/download/v1.2.0.1/cangjie-stdx-windows-x64-1.2.0.1.zip`

opengauss-driver 从 `https://gitcode.com/Cangjie-TPC/opengauss-driver.git` 克隆，
并自动应用 `scripts/patch-driver.py`（幂等补丁）。

### 5.3 runner 与工具链

工作流使用 **GitHub 托管 runner**（`windows-latest`）：

```yaml
runs-on: windows-latest
```

**关键问题：托管 runner 上没有仓颉 SDK，且 SDK 不在公开仓库里。**

实测（2026-10-26）：仓颉 SDK 1.2.0 的 Windows 安装包**不是公开 gitcode release 资产**
（`Cangjie/cangjie_stdx/releases` 有 stdx，SDK 二进制没有；官方下载页的直链由前端动态生成）。

**解决方案：自举 —— 把工具链做成 Release 资产。**

```bash
# 本机执行一次（需 GITHUB_TOKEN）
export GITHUB_TOKEN=ghp_xxx
bash scripts/ci/publish-toolchain.sh
```

它会把 SDK（252 MB）与 stdx（6.6 MB）打包，传到 `toolchain-v1.2.0` 这个 Release，
CI 再从那里下载。**一次性成本，后续每次 CI 都是缓存命中。**

> ⚠️ **打包时自动补齐 MinGW 运行库**：仓颉 SDK 1.2.0 的 Windows 包本身**不含**
> `libgcc_s_seh-1.dll` / `libwinpthread-1.dll` / `libssp-0.dll`，
> 而 cjc 编译 `@Test` 用例时需要它们（缺了报 "could not find the create task
> method: RunCJTask"）。`publish-toolchain.sh` 会自动从 `tools/cangjie/bin`
> 或 Git for Windows 的 `mingw64/bin` 补齐，**找不到就拒绝打包**。
>
> 该链路已实测：解压工具链资产 → `cjc 1.2.0` 编译 `@Test` 程序 → 测试运行通过。

**仓库变量**（Settings → Secrets and variables → Actions → **Variables**）：

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `CANGJIE_TOOLCHAIN_TAG` | `toolchain-v1.2.0` | 工具链 Release 的 tag |

`setup-toolchain.sh` 的工具链来源优先级：

1. 已有 SDK（`CANGJIE_HOME` / 仓库内 `tools/cangjie/`）
2. **GitHub Release 工具链资产**（`CANGJIE_TOOLCHAIN_TAG`，推荐）
3. SDK 直链（`CANGJIE_SDK_URL`）

> SDK 与 stdx 都用 `actions/cache` 缓存（key `ams-toolchain-<os>-1.2.0`），
> 第二次起 CI 不再下载。

### 5.4 需要的 Secrets

| Secret | 用途 | 必需 |
| --- | --- | --- |
| `GITHUB_TOKEN` | 自动生成（发 Release 用） | ✅（工作流自动注入） |
| `AMS_DB_PASSWORD` | CI 集成测试连数据库 | 可选（无则跳过集成测试） |

## 6. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `error while loading shared libraries` | 缺运行时 DLL | 确认 `bin/` 下有 `libstdx.*`、`libcangjie-*`、`libgcc_s_seh-1.dll`、`libwinpthread-1.dll`、`libpcre2-8.dll` |
| `could not find the create task method: RunCJTask` | MinGW 运行库缺失 | 同上（这是 SDK 1.2.0 的已知缺件） |
| `Invalid username/password (28P01)` | 口令被 percent-encode | 去掉 `%XX` 编码，原样填入 |
| 启动即退出，日志 `server.db.unavailable` | 数据库连不上 | 检查 DB 地址/端口/防火墙；确认 openGauss 容器在跑 |
| `AMS_TOKEN_SECRET 未设置` | 必填项缺失 | 按提示设置 |
| 端口被占用 | 冲突 | 改 `AMS_HTTP_PORT` |
| `gh: command not found` | 未装 gh | 用 `scripts/release.sh`（走 REST API，无需 gh） |
| 打包报「缺少必需的运行时 DLL」 | `build/` 下的 DLL 不全 | 先跑 `bash scripts/build.sh` 生成完整产物 |
| CI 报 `could not find the create task method: RunCJTask` | 工具链包缺 MinGW 运行库 | 重新执行 `bash scripts/ci/publish-toolchain.sh`（会自动补齐） |
| CI 报「工具链资产下载失败」 | Release 资产不存在，或私有仓库未注入 token | 确认 `toolchain-v1.2.0` Release 存在；私有仓库需 `GITHUB_TOKEN` |

## 7. 版本与校验

```bash
# 校验发布包完整性
sha256sum -c CHECKSUMS.sha256          # Linux
certutil -hashfile ams-release-0.2.0-windows-x86_64.zip SHA256   # Windows
```

版本号遵循语义化版本。`CHANGELOG.md` 里对应版本的段落会被自动抓取为
GitHub Release 的说明。
