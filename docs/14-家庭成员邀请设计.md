# 14 · 家庭成员邀请与轻量协作 · 设计文档

> 对应需求：**SC-12**（家庭成员邀请与轻量协作）、**FR-ACL-010**（家庭成员邀请：邀请码/二维码；成员仅可见显式授权内容）
> 关联需求：FR-ACL-001~009（授权共享与回收）、FR-ACL-013（权限预览）
> 状态：**设计稿（未实现）** · 版本：v1 · 日期：2026-10-29
> 适用代码基线：`main`（P2 进行中，已完成 11/23）

---

## 0. 一句话结论

家庭协作的**唯一安全底线**是：**成为家庭成员 ≠ 获得任何数据访问权**。
成员能看到的每一条数据，都必须来自一条**显式、可过期、可撤销、留痕**的授权记录。
邀请只解决「把人拉进组」，绝不顺带解决「给他看什么」。

---

## 1. 背景与目标

### 1.1 业务背景

现有系统已支持「本人档案」与「机构内按角色/主体授权」（FR-ACL-001~009）。
但家庭场景（配偶代办、子女代管老人证件、父母查看子女学籍）缺少一条**低门槛、可解释、可收回**的协作路径：

- 让家人注册成机构用户并分配角色，过重且语义错误；
- 直接把账号口令给对方，等于放弃追责与撤销能力；
- 公开共享链接（FR-ACL-011）只读且面向「任何人」，不适合长期家庭协作。

### 1.2 目标

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G1 | 用邀请码/二维码把家人拉入「家庭组」 | 生成 → 扫码/输码 → 入组，全程 ≤ 3 步 |
| G2 | 入组后**默认什么都看不到** | 新成员登录后条目列表为空 |
| G3 | 所有者按「条目 / 分类 / 主体」显式授权 | 授权后成员仅能看到被授权范围 |
| G4 | 授权可设有效期、可随时撤销、到期自动失效 | 撤销/到期后下一次请求即 403/404 |
| G5 | 全过程可审计、可举证 | 邀请、入组、授权、撤销、移除均有审计事件 |
| G6 | 邀请凭据不可猜测、不可重放、不可长期有效 | 见 §7 威胁模型与控制 |

### 1.3 非目标（明确不做）

- ❌ 家庭成员之间的**写协作**（共同编辑同一条目）——P3 再议；
- ❌ 家庭组内的**审批流**（如「子女申请查看，父母审批」）——P3 再议；
- ❌ 跨家庭组的数据共享与转授权；
- ❌ 通过邀请直接获得任何管理类权限（`system:*` / `acl:manage` / `audit:read`）。

## 2. 术语与角色

| 术语 | 定义 |
| --- | --- |
| 家庭组（Family Group） | 协作的最小单元。一个用户可创建/加入多个组（如「我的小家」「父母家」） |
| 组所有者（Owner） | 创建者。唯一有权邀请、授权、移除成员、解散组 |
| 组管理员（Manager，可选） | 由 Owner 指定，可邀请与授权，但**不能**移除 Owner / 解散组 |
| 家庭成员（Member） | 被邀请入组者。**默认零可见**，仅能读取被显式授权的内容 |
| 邀请（Invite） | 一次性的入组凭据，含 code（人输）与 link（扫码）两种载体 |
| 授权（Grant） | 一条 `acl_grants` 记录：`(grantee, 资源类型, 资源 ID, 权限, 有效期)` |

> **角色与系统 RBAC 的关系**：家庭角色是**组内角色**，不写入 `sys_user_roles`。
> 成员的全局权限仍然只有系统角色（默认 `user`）。家庭组内的可见性由 `acl_grants` 决定，
> 避免「入组即提权」这类结构性风险。

## 3. 核心安全原则（设计约束，不可妥协）

1. **默认拒绝（Default Deny）**
   无授权 = 不可见。列表查询必须**先算可见集合**再查数据，禁止「查全量再过滤」。
2. **显式授权（Explicit Grant）**
   授权必须指名「谁 + 什么资源 + 什么权限 + 到什么时候」，缺一不可。
3. **最小权限（Least Privilege）**
   成员默认仅有 `archive:read:own`（读被授权内容）；无写、无删、无导出、无分享。
4. **凭据不可猜测（Unguessable）**
   邀请 code 由 CSPRNG/密钥派生，≥ 40 bit 熵；链接 token ≥ 128 bit 熵。
5. **短时效 + 一次性（Short-lived & Single-use）**
   默认 15 分钟、1 次；可配上限 24 小时、10 次。
6. **不可枚举（No Enumeration）**
   邀请校验失败、被邀请人不存在、已入组，对外**统一错误文案与状态码**。
7. **可撤销（Revocable）**
   邀请可撤销；成员可移除；授权可撤销；三者的生效时间都是「下一次请求」。
8. **全程留痕（Auditable）**
   邀请创建/接受/撤销、成员加入/移除、授权创建/撤销，全部落审计链。
9. **不越权授权（No Privilege Escalation）**
   授权人只能授出**自己拥有**的权限；被授出的权限不得超过授权人的数据可见上限。
10. **数据最小化（Data Minimization）**
    成员可见的字段按 `sensitivity` 逐级掩码；附件、扩展字段默认不随条目授权自动可见。

## 4. 数据模型

### 4.1 新增表

```sql
-- 家庭组
CREATE TABLE IF NOT EXISTS fam_groups (
    id          BIGINT       PRIMARY KEY,
    name        VARCHAR(64)  NOT NULL,
    owner_id    BIGINT       NOT NULL,
    status      SMALLINT     NOT NULL DEFAULT 0,   -- 0 正常 / 1 已解散
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    version     INT          NOT NULL DEFAULT 1
);

-- 组成员（组内角色与全局 RBAC 解耦）
CREATE TABLE IF NOT EXISTS fam_members (
    id          BIGINT       PRIMARY KEY,
    group_id    BIGINT       NOT NULL,
    user_id     BIGINT       NOT NULL,
    role        VARCHAR(16)  NOT NULL DEFAULT 'member',  -- owner / manager / member
    status      SMALLINT     NOT NULL DEFAULT 0,         -- 0 正常 / 1 已移除
    invited_by  BIGINT       NOT NULL DEFAULT 0,
    joined_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    removed_at  TIMESTAMPTZ,
    removed_by  BIGINT
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_fam_members
    ON fam_members(group_id, user_id);
CREATE INDEX IF NOT EXISTS idx_fam_members_user ON fam_members(user_id);

-- 邀请（只存 code 的加盐摘要，不存明文）
CREATE TABLE IF NOT EXISTS fam_invites (
    id           BIGINT       PRIMARY KEY,
    group_id     BIGINT       NOT NULL,
    inviter_id   BIGINT       NOT NULL,
    code_hash    VARCHAR(128) NOT NULL,
    code_salt    VARCHAR(64)  NOT NULL,
    target_role  VARCHAR(16)  NOT NULL DEFAULT 'member',
    max_uses     INT          NOT NULL DEFAULT 1,
    used_count   INT          NOT NULL DEFAULT 0,
    fail_count   INT          NOT NULL DEFAULT 0,
    max_fails    INT          NOT NULL DEFAULT 5,
    expires_at   TIMESTAMPTZ  NOT NULL,
    revoked      BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_fam_invites_group ON fam_invites(group_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_fam_invites_expires ON fam_invites(expires_at)
    WHERE revoked = FALSE;
```

### 4.2 复用既有表

| 表 | 用途 | 说明 |
| --- | --- | --- |
| `acl_grants` | 显式授权（已有，FR-ACL-008） | 新增 `group_id` 可空列，便于「按组撤销」与审计聚合 |
| `sys_audit_log` | 审计链（已有） | 新增动作码见 §8 |
| `arc_items` / `arc_item_fields` | 被授权资源 | 不改结构 |

> **不新增「可见性物化表」**：可见集合始终由 `acl_grants` **实时计算**。
> 物化视图会引入「撤销后仍有缓存副本」的一致性问题，对隐私系统不可接受。

## 5. 邀请流程

### 5.1 时序（邀请方 → 被邀请方）

```
Owner                     服务端                        被邀请人
  │  POST /family/groups/:id/invites
  │─────────────────────────▶│
  │                          │ 1. 校验 Owner/Manager 身份
  │                          │ 2. 生成 code(8位Base32,40bit) + token(128bit)
  │                          │ 3. 仅存 HMAC-SM3(salt, code) 与 token 摘要
  │                          │ 4. 写审计 invite.create
  │◀── {code, link, qr, expiresAt, maxUses}
  │   （线下/当面告知 code；或展示二维码）
  │                                                      │
  │                                                      │ 扫码打开 /invite/:token
  │                                                      │──────────────▶ GET /family/invites/:token
  │                                                      │◀── {groupName, inviterNick, expiresAt}
  │                                                      │ 输入/确认 code
  │                                                      │──────────────▶ POST /family/invites/accept
  │                          │ 1. 校验 code 摘要 + 有效期 + 次数
  │                          │ 2. 写入 fam_members（role=member）
  │                          │ 3. used_count+1，达上限即失效
  │                          │ 4. 审计 invite.accept
  │                          │◀── {groupId, role:"member"}
  │  （此时成员可见 0 条 —— 默认拒绝）
```

### 5.2 邀请码 vs 二维码

| 载体 | 形式 | 优点 | 风险 | 控制 |
| --- | --- | --- | --- | --- |
| 邀请码 | 8 位 Base32（去掉 0/O/1/I/L） | 可口头/短信传达 | 可能被肩窥、截图转发 | 15 分钟 + 1 次 + 失败上限 |
| 二维码 | `https://<host>/invite/<token>` | 扫码即达，体验好 | 截图外流、群聊转发 | 同上 + 短 TTL + 可撤销 |

> **二维码不含任何 PII**（不含姓名、手机号、组名明文），只含随机 token。
> 扫码落地页必须带 `Referrer-Policy: no-referrer`，避免 token 经 Referer 外泄。

### 5.3 边界与冲突处理

| 场景 | 处理 |
| --- | --- |
| 邀请自己 | 拒绝（400，文案不区分「自己是 owner」与「自己已入组」） |
| 已是同组成员 | **幂等成功**（不重复插入，`used_count` 不增加），返回 `alreadyMember = true` |
| 已在**其他**家庭组 | 允许（一个用户可属于多个组） |
| 邀请已过期 / 已撤销 / 次数用尽 | 统一 `404`，文案「邀请无效或已过期」 |
| code 连续错误 ≥ max_fails | 邀请立即 `revoked = TRUE`，后续一律 404 |
| 组已解散 | 拒绝，404 |

> **判定顺序（`acceptInvite` 实际实现，2026-10 落地时调整过）**：
> `token 定位 → **成员身份** → 状态有效 → code 正确 → 原子消耗次数 → 入组`
>
> 「成员身份」必须排在「状态」之前。原因是默认 `maxUses = 1`：家人第二次点同一个链接时，
> 邀请刚好已被他自己用尽，若先判状态就会看到「邀请不存在」——
> 而他明明已经在组里。这种「加入了却说邀请无效」的反馈会让人反复找邀请人重发。
> 提前判定不泄漏信息：能走到这一步说明**持有 token**（凭据已具备），
> 而「你在不在这个组里」对本人本来就不是秘密；非成员仍拿 404。

## 6. 授权模型（成员可见性的唯一来源）

### 6.1 授权粒度

> ✅ **已决策（docs/15 §5 · 方案 B）**：落地为**主体 + 条目两级**，
> 「分类」不单独成档，而是**同一主体内按分类收窄**。
> 理由是现有 `acl_grants.subject_id` 为 `NOT NULL`，`Grant.covers()` 的分类匹配
> 之后仍要求同主体 —— 「跨主体按类目共享」在当前数据模型上根本不成立；
> 若为它改造核心 ACL 表（放开 `subject_id` 可空），会让每一次既有授权判定都多一个分支，
> 收益远小于风险。分类收窄已经覆盖「各类目分享给不同家人」的真实需求。

| 粒度 | 落库形态 | 示例 | 说明 |
| --- | --- | --- | --- |
| 主体 | `item_id` NULL、`category` NULL/0、`subject_id` = 主体 | 授权「母亲」主体下全部条目 | 最常用，适合代办 |
| 分类（收窄） | `item_id` NULL、`category` = 分类码、`subject_id` 必填 | 授权「母亲」主体下的「健康信息」 | **同主体内**按类目收窄，不跨主体 |
| 条目 | `item_id` = 条目 ID、`subject_id` 必填（用于归属校验） | 授权单张「房产证」 | 最细，适合单点共享；服务端校验条目确属该主体 |

> **不做字段级授权**（FR-ACL-014 为 P3 预留）。字段可见性由 `sensitivity` 与成员数据上限决定，不单独授权。
>
> **为什么不是「跨主体分类」**：那需要一个与主体无关的授权轴，等于把「一条授权覆盖 N 个主体」
> 引入 ACL 核心，历史判权、审计追溯、撤销语义都要重做一遍。真要跨主体批量分享，
> 正确做法是**每个主体各授一条**（前端已提供主体选择器，操作成本可接受）。

### 6.2 授权记录字段

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `grantee_id` | 被授权用户 | 必须是本组成员 |
| `granted_by` | 授权人 | 必须是 Owner/Manager |
| `subject_id` | 档案主体 | **NOT NULL**；授权人必须拥有该主体 |
| `item_id` | 条目 ID | 可空；非空时校验条目确属 `subject_id` |
| `category` | 分类码收窄 | 0 = 不限（主体级）；>0 时要求同主体 |
| `perms` | `read`（本期仅读） | 不含 `write`，固定 `archive:read:own` |
| `expires_at` | 到期时间 | 可空（永不过期） |
| `revoked_at` | 撤销时间 | 非空即失效 |

> **与初稿的偏离**：初稿写的是 `resource_type` + `resource_id` 两个泛化字段。
> 落地时改成 `subject_id` / `item_id` / `category` 三列，直接复用既有的 `acl_grants`
> 表（不新造一张平行授权表），否则「共享链接」与「家庭授权」会形成两套判权逻辑。
> `resource_type` 现在由 `GrantScope.resourceTypeOf(itemId, category)` **计算得出**
> （条目 > 分类 > 主体），只用于展示与审计，不落库 —— 少一列就少一处不一致。

### 6.3 可见性判定顺序（服务端强制）

```
1. 用户已认证                     否 → 401
2. 用户在目标家庭组内且 status=0    否 → 403（不区分「不在组」与「已移除」）
3. 取该用户全部有效授权（未撤销、未过期）
4. 目标条目命中任一授权范围？        否 → 403（列表查询则直接不返回）
5. 条目 sensitivity <= 用户数据上限？ 否 → 返回但字段掩码（或按策略 403）
6. 审计（仅当发生「敏感明文」访问时）
```

> **性能约束**：列表查询必须把「授权范围」下推为 SQL 条件（`EXISTS (SELECT 1 FROM acl_grants ...)`），
> 不允许先拉全量再在应用层过滤。授权数超过阈值（如 200 条/人）时走 `acl_grants(grantee_id, resource_type)` 索引。

## 7. 威胁模型与控制

### 7.1 威胁清单

| # | 威胁 | 攻击面 | 影响 | 控制措施 |
| --- | --- | --- | --- | --- |
| T1 | 邀请码被暴力枚举 | `POST /invites/accept` | 未授权入组 | 40 bit 熵 + 失败上限 5 次 + 按 IP 限流 10 次/分 + 短 TTL |
| T2 | 邀请链接被转发/截图 | 二维码、链接 | 陌生人入组 | 一次性 + 15 分钟 + 可撤销 + 入组审计可追溯 |
| T3 | 入组即提权 | 角色映射错误 | 越权读写 | 家庭角色**不写入** `sys_user_roles`；成员全局权限不变 |
| T4 | 授权越权（授出自己没有的） | 授权接口 | 数据外泄 | 服务端校验「授权人可访问该资源」+「perms ⊆ 授权人 perms」 |
| T5 | 撤销不生效 | 缓存/物化视图 | 撤权后仍可见 | 可见性实时计算，不缓存；撤销写库即生效 |
| T6 | 枚举用户是否注册 | 接受邀请接口 | 账号探测 | 统一错误文案与状态码；不返回「该手机号未注册」 |
| T7 | 邀请 code 泄露到日志 | 访问日志 | 凭据泄露 | 日志只记 invite_id，**绝不记 code/token 明文** |
| T8 | 重放已接受的邀请 | 重放 accept | 重复入组 | `used_count` 原子自增 + 唯一索引 `(group_id, user_id)` |
| T9 | CSRF 伪造授权/移除 | 管理接口 | 越权操作 | Bearer Token（非 Cookie）+ 同源校验 + `Content-Type: application/json` |
| T10 | 成员被移除后会话仍可用 | 会话层 | 残留访问 | 移除时吊销该用户全部会话（`sessions.revokeAll`）+ 授权全撤 |
| T11 | 高敏字段经共享旁路泄露 | 条目详情/列表 | 隐私泄露 | `sensitivity > maxDataLevel` 字段掩码；附件不随条目自动可见 |
| T12 | 审计被篡改 | 审计表 | 无法举证 | 沿用现有 SM3 哈希链 + 审计表仅 INSERT/SELECT（受限角色） |
| T13 | 邀请接口被刷（DoS） | 创建邀请 | 资源耗尽 | 每用户 10 次/小时；全局限流中间件兜底 |
| T14 | 二维码指向钓鱼站 | 二维码 | 凭据被钓 | 链接固定同源域名；落地页展示组名+邀请人昵称供核对 |

### 7.2 密码学选择

| 用途 | 算法 | 理由 |
| --- | --- | --- |
| 邀请 code 摘要 | HMAC-SM3(salt, code) | 与全仓国密口径一致；code 熵低但短时效 + 失败上限已足够 |
| 邀请 token | HMAC-SM3(服务端密钥, 随机数) 取 128 bit | 不可预测、不可逆；密钥轮换即全量失效 |
| 审计链 | SM3 哈希链（已有） | 与现有 FR-AUD 一致 |

> **不以「加密」代替「摘要」**：邀请 code 不需要还原，只做比对，故用单向摘要。

## 8. 审计事件

| 动作码 | 触发 | 关键字段 |
| --- | --- | --- |
| `family.group.create` | 创建家庭组 | groupId, name |
| `family.group.dissolve` | 解散组 | groupId, memberCount |
| `family.invite.create` | 创建邀请 | groupId, inviteId, targetRole, maxUses, expiresAt |
| `family.invite.revoke` | 撤销邀请 | groupId, inviteId |
| `family.invite.accept` | 接受邀请 | groupId, inviteId, userId, result |
| `family.invite.fail` | code 错误 | inviteId, failCount, ip |
| `family.member.remove` | 移除成员 | groupId, userId, revokedGrants |

### 9.4 错误语义（统一，防枚举）

| 场景 | 状态码 | 文案 |
| --- | --- | --- |
| 非组内成员访问 | 403 | `无权访问该家庭组` |
| 邀请无效/过期/撤销/次数用尽 | 404 | `邀请无效或已过期` |
| code 错误 | 403 | `邀请码不正确`（**不透露剩余次数**，避免辅助爆破） |
| 资源不在授权范围 | 403 | `无权访问该条目` |
| 资源不存在 | 404 | `条目不存在` |

> 403 与 404 的分工：**已认证但无权** → 403；**凭据/资源不存在** → 404。
> 二者都不得泄露「资源是否存在」的额外信息（403 也不返回资源标题）。

| 页面 | 要点 |

## 12. 测试计划

### 12.1 单元测试

| 用例 | 断言 |
| --- | --- |
| code 生成 | 长度 8、字符集合法、10000 次无重复 |
| code 摘要 | 同 code 不同盐 → 不同摘要；摘要不可逆 |
| 过期判定 | `expires_at < now` → 无效 |
| 次数用尽 | `used_count >= max_uses` → 无效 |
| 失败上限 | 第 5 次错误 → `revoked = TRUE` |
| 授权越权 | 授权人无该资源权限 → 拒绝 |
| 权限子集 | 授出 `write` 而授权人只有 `read` → 拒绝 |
| 可见性计算 | 无授权 → 0 条；授权 subject → 仅该主体条目 |
| 掩码 | `sensitivity=3` 且上限=1 → issuer/remark 为空 |

### 12.2 集成测试（端到端）

1. A 创建组 → 生成邀请 → B 接受 → **B 列表为空**（关键断言）
2. A 授权 subject=X 给 B → B 仅见 X 下条目
3. A 撤销授权 → B 下一次请求即 403
4. A 移除 B → B 会话失效、授权全撤
5. code 错误 5 次 → 邀请失效，第 6 次 404
6. 邀请过期 → 404
7. 非组内用户访问组详情 → 403（不泄露组名）
8. B 尝试授权给 C → 403（member 无授权权）

### 12.3 安全测试

- 枚举：连续请求 1000 个随机 code，响应时间与文案无差异（防时序侧信道）。
- 越权：B 直接构造 `itemId` 访问未授权条目 → 403。
- 重放：同一邀请并发 accept 10 次 → 仅 1 次成功（`used_count` 原子性）。
- 日志：抓取服务端日志，确认无 code/token 明文。

## 13. 风险与未决问题

| # | 风险/问题 | 建议 |
| --- | --- | --- |
| R1 | 成员可见性实时计算，授权多时列表查询变慢 | 加 `acl_grants(grantee_id, resource_type, resource_id)` 复合索引；>500 条授权时告警 |
| R2 | 移除成员需吊销其全部会话，可能影响其个人使用 | 仅吊销「组内授权」相关缓存；全局会话吊销需二次确认（文案明示） |
| R3 | 一个用户属于多个组时的可见性叠加 | 取**并集**（授权是加法），但审计需标明来源组 |
| R4 | 家庭组解散后数据归属 | 只删组成员与授权，**不删任何条目**（条目属于主体所有者） |
| R5 | 二维码被拍照外传 | 短 TTL + 一次性 + 可撤销 + 入组审计；产品侧提示「当面发送」 |
| R6 | 是否需要「成员申请 → owner 审批」 | **已决策：不做**（docs/15 §4）。理由：邀请方向本就是 owner 主动发起，再加一个申请入口会开出「任何人可向任意组投递」的骚扰与枚举通道，与 §3「No Enumeration」正面冲突；而它要解决的问题（成员想加入某组）在现实中不存在 —— 组是私域，用户不该知道别人组的存在。若将来真要做，必须先有「组不可枚举」的独立设计 |
| R7 | 邀请 code 是否允许自定义（如 6 位数字） | **不允许**：自定义会显著降低熵，破坏 T1 控制 |
