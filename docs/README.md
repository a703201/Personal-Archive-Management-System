## 二、系统一句话定义

> **AMS 是一套面向个人/家庭全生命周期数字档案的私有化管理平台**：以国密算法为密码学底座，以开放Gauss 为数据底座，支持证件、学历、职业、资质、资产、健康、关系、影像附件等十余类档案的分类归档、全文检索、版本追溯、授权共享与全链路审计。

| D1 | 后端主语言 **Cangjie**，C++ 仅作性能/生态补齐 | 仓颉为国产化主推语言，静态编译、跨平台、字节码安全检查内建，契合信创与鲲鹏目标 | 全 Go / 全 Rust / Java | [架构 §2](./02-架构设计说明.md#2-技术选型与语言分工) |
| D2 | Web 前端**前后端分离 + SPA** | 交付形态最通用，桌面/平板/手机一套代码，响应式覆盖多端 | 服务端渲染 / 原生客户端 | [架构 §3](./02-架构设计说明.md#3-总体架构) |
| D3 | 密码存储用 **PBKDF2-HMAC-SM3 自研迭代**，不用裸 SM3 | 裸 SM3 计算太快，易被 GPU 爆破；PBKDF2 迭代是国密合规下的通行做法 | 纯 SM3 单次 / Argon2 / SM3+salt+万次迭代 | [安全 §4.1](./03-安全设计专章.md#41-口令存储) |
| D4 | 传输层用 **TLS 1.3 + 国密 TLS 可选**，字段级用 **SM4-CBC/CTR + HMAC-SM3（EtM 组合）** | TLS 保护链路，字段级加密保护落库数据。**SDK 的 stdx 不提供 SM4-GCM**（`create tag error`），故用「先加密再整体 MAC」的 Encrypt-then-MAC 构造补齐认证性，安全性等价于 AEAD | 依赖 SM4-GCM（不可用）/ SM4-CBC 裸用无 MAC / 仅依赖 TDE | [安全 §4.2](./03-安全设计专章.md#42-传输加密) · [SM4 方案变更](./08-SM4方案变更说明.md) |
| D5 | 高敏字段（证件号/手机/银行卡）**字段级 SM4 加密 + 密文等值查询** | 复用 openGauss 密态等值查询的确定性加密能力（CMK/CEK 模型） | 全表 TDE / 应用层全字段加密不做检索 | [安全 §4.3](./03-安全设计专章.md#43-字段级加密与密态检索) |
| D6 | 敏感值另存 **SM3 盲索引（blind index）** 列 | 在无法依赖数据库端密态能力时，兼顾"加密存储 + 可等值检索" | 仅存密文放弃检索 / 全量明文 | [安全 §4.3](./03-安全设计专章.md#43-字段级加密与密态检索) |
| D7 | 附件**元数据入库、字节流落对象存储**，附件本身 SM4 加密 | 元数据可检索可事务，字节流走对象存储避免 DB 大对象膨胀 | 全部 blob 入库 / 明文落盘 | [数据模型 §7](./06-数据模型设计.md#7-附件与影像实体) |
| D8 | RBAC 采用 **用户—角色—权限** 三段式 + 数据归属（ownership）双层 | 权限既能按角色授予，又能按数据归属收敛，兼顾"管理员能管"和"用户只能看自己" | 纯 ACL / 纯 RBAC / ABAC 全量 | [PRD §5.4](./01-PRD-产品需求文档.md#54-权限与角色模型fr-acl) |
| D9 | 交付**二进制 + Docker 双形态**，构建矩阵 x86_64/aarch64 × Linux/Windows | 二进制适合鲲鹏裸机与国产化环境，Docker 适合快速部署与编排 | 仅二进制 / 仅容器 | [架构 §7](./02-架构设计说明.md#7-跨平台与多架构构建发布) |
| D10 | 视觉层**深浅色双主题 + 语义化设计令牌 + 弹簧动效** | 苹果风的核心是"层次与克制"，用令牌系统而非硬编码颜色实现可维护 | 单一浅色 / 引入完整组件库 | [视觉 §2](./07-视觉与交互设计规范.md#2-设计令牌) |
| D11 | 导出**四层管控**（权限 / 二次确认 / 限流 / 留痕告警）+ 敏感字段默认导出密文 | 导出是数据离开系统的唯一通道，风险等同大规模泄露；默认导出密文避免明文在下载目录裸奔 | 导出仅做权限校验 / 明文导出 / 不做导出 | [安全 §6.5](./03-安全设计专章.md#65-导出功能安全设计专节) |
| D12 | 导出走**异步任务**（统一导入导出任务表），M3 先交付同步版 | 全量导出同步必然超时且无法反馈进度；异步化涉及任务表与调度，排在 M4 | 全同步 / 一开始就全异步 | [架构 §6.3.1](./02-架构设计说明.md#631-导出任务执行模型) |

## 五、文档使用约定

- **状态标记**：`【已定】` 表示本轮达成共识、可直接指导实现；`【待定】` 表示需在对应里程碑前由指定角色确认；`【预留】` 表示本期不做但预留扩展点。
- **优先级**：P0 必须有 / P1 应该有 / P2 可以有 / P3 将来做；MoSCoW 记法中 Must= P0+P1，Should=P2，Could/Won't=P3。
- **编号规则**：需求用 `FR-<域>-<序号>`（如 `FR-AUTH-003`），非功能需求用 `NFR-<类别>-<序号>`，风险用 `R-<序号>`，架构决策用 `D-<序号>`（与 §三一致），测试用例用 `TC-<模块>-<序号>`。
- 所有表结构、接口、错误码示例均为**设计基线**，实现阶段如有偏离须走 ADR 流程回写本目录。

>   - `StorageProviders` 注册表提供 **8 个平台**：`local`（本地 FS，默认且唯一完全可用）/ `minio` / `huawei`（华为云 OBS）/ `aliyun`（阿里云 OSS）/ `qiniu`（七牛 Kodo S3 兼容网关）/ `tencent`（腾讯云 COS）/ `aws` / `s3`；每家带 endpoint 模板、region 样例、桶命名约束、默认寻址风格与签名协议。
>   - **平台选择接口**：`GET /api/admin/storage/providers`、`GET|PUT /api/admin/storage/config`（`cfg:read` / `cfg:manage`，写 `deployment.env`，重启生效，凭据脱敏）；切换时做**存量附件保护**，防旧 `storage_key` 失效。
>   - **HMAC-SHA256 已补**：RFC 2104 + stdx SHA256 原语实现，RFC 4231 四个向量（含 131 字节长 key）验证；`ams.crypto.impl` 不再返回「暂未接入」。
>   - **SigV4 签名计算已实现**：`sigv4.cj` 用 AWS 官方 GET Object 向量验证，供各家 S3 兼容接口共用；七牛自有 QiniuV2 / 阿里 OSS 自有 V1 签名明确标注「未实现」。
>   - `arc_attachments` 新增 `storage_provider` 列（迁移 025），每行自述厂商，与 `storage_backend`(0/1) 互补；存量行回填 `local`。
> - ✅ **`S3Transport`（HTTP 客户端）已补齐**：新增 `http_transport.cj` 的 `HttpS3Transport`，基于 `std.net`（TcpSocket）+ `stdx.net.tls`（TlsSocket）自实现 HTTP/1.1 客户端，PUT/GET/DELETE 真正发出；**404 → None、其余失败关闭**（连接/签名/响应失败一律 `StorageFailure`，绝不静默回落 FS 或明文写入）。选择非 `local` 平台在配置完整时即构建真实传输层（不再仅因缺 transport 启动即失败关闭）。`StorageAdminRoutes` 的 `transportReady` 改为按平台能力返回 `true`。详见 `docs/10` 第六/七批与「真实 S3/OBS HTTP 传输层落地」章节、`CHANGELOG.md [1.3.0]`、`http_transport.cj` 头注释。
> - 详见 `docs/10` 第六/七批、`CHANGELOG.md [1.3.0]`、`http_transport.cj` / `providers.cj` / `sigv4.cj` 头注释。

> **Q2 最终选型（2026-11-12 定稿）**：经运维 / 甲方确认，**最终选型为「默认本地 FS 或自建 MinIO，云 OBS 作为可选接入项」**——对外暴露 8 选 1 平台（local / minio / huawei / aliyun / qiniu / tencent / aws / s3），部署默认维持 A 或 B，C 作为按需可选项不强制上云。下方为明确的推荐顺序与切换触发条件：
>
> | 方案 | 适用条件 | 成本 | 主要风险 | 本仓就绪度 |
> | --- | --- | --- | --- | --- |
> | **A 继续本地 FS** | 单实例 / 单租户、附件量小、私有离线部署、无机房外网 | 零额外成本、零运维 | 单点故障、扩容与备份全靠手工；磁盘写满即失败关闭 | 默认 `local`，`StorageBackends.make()` 直接装配 `LocalFileStorage`，行为零回归 |
> | **B 自建 MinIO** | 需要容器编排 / 多实例共享附件、数据必须留在自有环境、要真实验证 S3 兼容链路 | 一台常驻容器（compose `--profile s3` 已预置）+ 自维护升级 / 监控 | 自维护 HA、磁盘与凭据；切换前必须完成存量迁移（见 `docs/16`） | `sigv4.cj` + `HttpS3Transport` 已落地；`AMS_IT_MINIO=1 bash scripts/test.sh ams-storage` 可端到端复验（一键脚本 `scripts/ci/verify-minio.sh`；2026-11-12 已用 `scripts/ci/verify-s3-moto.sh` 经 moto 真实往返实测，免 Docker） |
> | **C 云 OBS（华为 / 阿里 / 腾讯）** | 跨地域访问、弹性容量、不愿自维护存储 | 按量付费 + 出口流量费 + 合规评估 | 厂商锁定、跨境 / 数据合规、AK/SK 托管；桶策略禁公共读须运维在控制台落实 | 8 个平台 profile 齐备，均走 S3 兼容 SigV4；真实连通性依赖厂商侧配置，本仓无法离线证明 |
>
> **推荐顺序（明确，不模棱两可）**：**A（当前默认，继续维持）→ B（第一次真实切换的优先目标）→ C（最后评估）**。
> - **维持 A**：当前是单实例 / 默认租户部署，本地 FS 是唯一「完全可用且零回归」的后端，没有理由为了上对象存储而上对象存储。
> - **切到 B 的触发条件**（满足任一即启动迁移）：① 单机磁盘或备份窗口成为瓶颈；② 需要多实例 / 横向扩展共享同一份附件；③ 需要用真实 S3 兼容链路做上线前演练。B 优先于 C，因为它是唯一能在自有环境、用 `verify-minio.sh` 一键端到端验证、且不引入合规与付费变量的选项。
> - **再评估 C 的触发条件**：B 已稳定且运维 / 甲方确认预算与数据合规（含跨境评估）后再切换；`providers.cj` 的 `huawei` / `aliyun` / `tencent` profile 与 `GET /providers` 下拉已就绪，切换动作与 B 相同，但**桶策略禁公共读、AK/SK 注入必须在厂商控制台完成**。
> - **任何 A↔B↔C 切换的前提**：先按 `docs/16` 完成预检与逐批迁移；库内已有附件时 `PUT /api/admin/storage/config` 改 provider / endpoint / bucket 会返回 Conflict，这是防 `storage_key` 静默失效的保护，不是故障。
>
> **结论一句话**：**Q2 已定稿**——默认采用「本地 FS（A）」或「自建 MinIO（B）」，并提供「云 OBS（C：华为 / 阿里 / 腾讯等）」作为可选接入项，多平台经管理页 `SystemView` 与 `GET /api/admin/storage/providers` 暴露。当前部署维持 A；需要共享附件 / 横向扩展 / 上线前演练时优先切 B（可一键 `verify-minio.sh` 或免 Docker 的 `verify-s3-moto.sh` 端到端验证）；C 在合规与预算确认后再按需启用。
