# 08 · SM4 方案变更说明（SM4-GCM → SM4-CBC + HMAC-SM3）

> 状态：**已实施并验证**（2026-10-26）
> 影响范围：`ams-crypto`（密码学提供者、密钥管理）、`ams-core`（附件加密）
> 依据文档：[03-安全设计专章](03-安全设计专章.md) §4.3 字段级加密、§4.6 密钥管理

---

## 0. 结论摘要

| 问题 | 结论 |
| --- | --- |
| **变更方案是什么？** | 用 **SM4-CBC + HMAC-SM3 的 Encrypt-then-MAC（先加密后认证）组合**替代 SM4-GCM。三个使用点（密码学提供者、密钥包裹、附件加密）已全部改造完毕，并新增算法标识 `alg` 使包裹结果**自描述**。 |
| **现行版本支持 SM4-GCM 吗？** | **不支持。** 在 stdx **1.0.5.1** 与 **1.2.0.1** 上均实测失败：`Encrypt failed due to create tag error.`（OpenSSL 3.5.7 本身支持 SM4-GCM，问题在 stdx 的封装）。 |
| **变更必要吗？** | **必要，且无替代路径。** GCM 是本项目唯一的 AEAD 候选；它不可用时，若仍要提供「加密 + 完整性」的组合语义，只能用 EtM 手工组合（CBC + HMAC）。若退化为纯 CBC 不加 MAC，则**丢失完整性保护**，属于安全性倒退，不可接受。 |

**一句话**：这不是「降级方案」，而是**在 GCM 不可用时的标准替代做法**（NIST SP 800-38C 明确允许用 Encrypt-then-MAC 组合构造 AEAD 语义），且已通过密钥分离加固。

## 1. 能力基线（实测数据，非推测）

### 1.1 stdx 1.2.0.1 实测结果

在 SDK 1.2.0 / stdx 1.2.0.1 上直接调用 stdx 的密码学 API：

| 能力 | 状态 | 实测输出 |
| --- | --- | --- |
| SM3 摘要 | ✅ 可用 | `len=32` |
| HMAC-SM3 | ✅ 可用 | `len=32` |
| SM4-CBC | ✅ 可用 | `ct.len=32`（16 字节对齐） |
| SM4-CTR | ✅ 可用 | `ct.len=30`（流模式不填充） |
| **SM4-GCM** | ❌ **不可用** | `Encrypt failed due to create tag error.` |

复现方式（最小用例）：

```cangjie
import std.crypto.cipher.*
import stdx.crypto.crypto.*

let key = Array<Byte>(16, repeat: 0x01u8)
let iv  = Array<Byte>(16, repeat: 0x02u8)
let c = SM4(OperationMode.GCM, key, iv: iv)
c.encrypt("hello".toArray())   // → Encrypt failed due to create tag error.
```

### 1.2 变更历史

| 日期 | stdx 版本 | 结论 | 处置 |
| --- | --- | --- | --- |
| 2026-10-25 | 1.0.5.1 | SM4-GCM 不可用 | 采用 SM4-CBC + HMAC-SM3 |
| **2026-10-26** | **1.2.0.1** | **SM4-GCM 仍不可用**（SDK 大版本升级**未改变**这一事实） | 方案维持不变；顺带记录 SM4-CTR 可用 |

> 这条复测很关键：SDK 从 1.0.5 LTS 升到 1.2.0 STS 是大版本跨越，
> 原本有理由期待 GCM 被修复。**实测证明没有**，所以方案不需要重新评估。

### 1.3 失败原因分析

`create tag error` 发生在 stdx 内部的 **GCM 标签计算**环节。
OpenSSL 3.5.7 原生支持 SM4-GCM，因此**不是底层算法缺失**，而是 stdx 对
GCM 模式的封装存在缺陷（疑似：SM4 的块长/GCM 参数组合下标签计算分支
未正确处理，或 OpenSSL EVP 层对 SM4-GCM 的 tag length 约定不一致）。

这属于**上游 stdx 的问题**，本项目无法在应用层绕过（不能自己实现 GCM：
需要 GHASH 与 CTR 模式的组合实现，成本高且难以保证与国标/OpenSSL 逐字节一致）。

## 2. 变更方案

### 2.1 总体构造：Encrypt-then-MAC

```
明文 P
  │
  ├─ ① 加密：  C = SM4-CBC(encKey, IV, P)              ← 加密子密钥
  │
  ├─ ② 认证：  T = HMAC-SM3(macKey, header || IV || C)  ← 认证子密钥（独立）
  │
  └─ 输出：    ciphertext = header || IV || C || T
```

**顺序铁律：先加密、后认证**（EtM），解包时**先验 MAC、再解密**。
理由：若先解密后认证，攻击者可通过提交畸形密文观察解密行为差异，
形成 **padding oracle** 攻击面。EtM 把「密文是否被篡改」的判断完全前置到
解密之前，不产生该类侧信道。

### 2.2 与 GCM 的语义对比

| 维度 | SM4-GCM（不可用） | SM4-CBC + HMAC-SM3（本方案） |
| --- | --- | --- |
| 认证标签 | 16 字节 GCM tag | 32 字节 HMAC-SM3（更长，更难伪造） |
| 密钥 | 单密钥 | **两把独立子密钥**（encKey / macKey） |
| IV/nonce | 96-bit（12 字节），GCM 下严禁复用 | 128-bit（16 字节），随机生成，**允许**跨密钥复用（只要密钥不同） |
| 密文调包防护 | 靠 AAD 绑定上下文 | 靠 **把上下文放进 MAC 覆盖范围**（等效于 AAD） |
| 长度扩展攻击 | GCM 内部处理 | HMAC-SM3 天然免疫（HMAC 构造本身防长度扩展） |
| 附加数据 | 原生支持 | 把上下文并入 MAC 输入即等效 |
| 实现复杂度 | 低（库直接支持） | 中（需手工组合，但结构简单） |

**结论**：EtM 组合在语义上**完整覆盖**了本项目对 AEAD 的需求
（机密性 + 完整性 + 上下文绑定），不存在能力缺口。

### 2.3 三个使用点的具体改造

#### ① 密码学提供者（`ams.crypto.impl` / `ams.crypto.provider`）

`CryptoProvider.encrypt/decrypt` 的 `CipherMode` 枚举**只提供 `Cbc` 与 `Ctr`**，
**不提供 `Gcm`**。即：**GCM 在接口层面就被排除了**，调用方无法误用。

```cangjie
match (mode) {
    case CipherMode.Cbc => return Some(SM4(OperationMode.CBC, key, iv: iv))
    case CipherMode.Ctr => return Some(SM4(OperationMode.CTR, key, iv: iv))
}
```

#### ② 密钥包裹（`ams.crypto.key`）

```
存储：  storageKeyLen(1) | storageKey | nonce(16) | ciphertext | hmac(32)
        storageKey = "keyId:vN:a2"     ← a2 = alg=2（分离派生）
        明文 = storageKey || DEK        ← storageKey 前缀便于解包时定位密钥
MAC 覆盖： storageKey || nonce || ciphertext
```

**本次变更额外修复了密钥分离问题**（见 §4）。

#### ③ 附件加密（`ams.core.attachment`）

```
密文布局（32 字节头 + 密文 + 32 字节 MAC）：
  偏移  0    4     5     6  7     8              16            32
       magic alg  ver  reserved  origLen(8)     iv(16)        ciphertext
      "AMSC"  1    1     0  0                                 ... + hmac(32)

  magic   = 0x414D5343 ("AMSC")   文件类型校验，防误用
  alg     = 1                     算法标识（SM4-CBC + HMAC-SM3）
  ver     = 1                     格式版本
  origLen = 明文长度              解密后校验，防止截断/填充歧义
  MAC 覆盖 = magic..ciphertext    即整个头部 + 密文
```

**头部进 MAC 覆盖范围**是关键设计：`alg`、`ver`、`origLen` 都被认证，
攻击者无法篡改算法标识或截断长度字段。

### 2.4 上下文绑定（等效 AAD）

GCM 的 AAD（附加认证数据）用于把密文绑定到上下文，防止「密文调包」。
EtM 组合的等效做法是**把上下文并入 MAC 输入**：

- 附件：MAC 覆盖整个头部（含 `alg`/`ver`/`origLen`）+ IV + 密文
- 密钥包裹：MAC 覆盖 `storageKey`（含 keyId 与版本）+ nonce + 密文

即：**密文与它的上下文绑定在同一个认证标签下**，跨主体/跨字段搬运密文会导致 MAC 校验失败。

## 3. 变更的必要性论证

### 3.1 为什么不能「什么都不做」

若保持 GCM 的设计文档而不改代码：

1. **代码根本无法编译**（`CipherMode.Gcm` 不存在）或运行期直接失败；
2. 字段级加密与附件加密这两个**核心安全能力缺失**，敏感字段只能明文存储 —— 直接违反安全目标 §1.1。

### 3.2 为什么不能「退化为纯 SM4-CBC（不加 MAC）」

纯 CBC 只保证机密性，**不保证完整性**：

- 攻击者可篡改密文 → 解密得到被篡改的明文（**没有检测手段**）；
- 可实施 **padding oracle** 攻击（若应用层对填充错误有差异化响应，可逐字节恢复明文）；
- 不满足「密文调包防护」「上下文绑定」等需求。

**这是安全性倒退，不可接受。**

### 3.3 为什么不能「自己实现 SM4-GCM」

技术上可行（CTR 模式 + GHASH），但：

- 需自行实现 GHASH 并处理 GCM 的域分离、长度字段、tag 截断等细节；
- 很难保证与 OpenSSL / 国标实现**逐字节一致**（跨语言互通、密文迁移会出问题）；
- 引入自研密码代码 = 引入新的攻击面与合规审查负担。

**投入产出比不划算**，且 stdx 的 `SM4-CTR` 已可用，纯粹为拼 GCM 而自研 GHASH 属于过度工程。

### 3.4 为什么 EtM 是标准做法

NIST SP 800-38C（推荐 GCM 模式的指南）明确说明：若 AEAD 不可用，
**可以用 Encrypt-then-MAC 组合构造等效的 AEAD 语义**，并给出了构造要求
（独立密钥、覆盖 IV/密文/上下文的 MAC、先验证后解密）。本方案逐条满足。

### 3.5 结论

| 选项 | 结论 |
| --- | --- |
| 保持 GCM 不变 | ❌ 不可行，代码跑不起来 |
| 纯 CBC 无 MAC | ❌ 安全性倒退，丢失完整性保护 |
| 自研 SM4-GCM | ❌ 过度工程，跨语言一致性风险高 |
| **SM4-CBC + HMAC-SM3（EtM）** | ✅ **标准替代做法，本项目采用** |

## 4. 本次变更同时修复的规范性问题：密钥分离

### 4.1 问题

改造前的 `KeyManager.wrap` 用**同一把 KEK** 同时做加密与认证：

```cangjie
let ciphertext = this.provider.encrypt(kek, nonce, plain, CipherMode.Cbc)  // KEK 加密
let mac = this.provider.hmac(kek, macInput, DigestAlgorithm.Sm3)            // KEK 认证
```

这违反了**密钥分离**原则：加密密钥与认证密钥应当相互独立。
一旦 KEK 泄露，攻击者同时获得加密与伪造认证的能力。

（附件加密那边没有这个问题 —— 它用 DEK 做 MAC，与加密用的 DEK 属同一数据密钥，
这是数据密钥的正常用法；问题只在**密钥包裹**这一层。）

### 4.2 修复

引入算法标识 `alg`，并从 KEK 派生出两把独立子密钥：

| alg | 含义 | 用途 |
| --- | --- | --- |
| `1` | `algReuseKek` —— 直接复用 KEK | **历史格式**，仅用于解开旧数据 |
| `2` | `algDerivedSubkeys` —— 分离派生 | **当前默认** |

派生方式（带用途标签的域分离）：

```
encKey = SM3("AMS-KEK-ENC-v1" || 0x00 || KEK)[0..16]
macKey = SM3("AMS-KEK-MAC-v1" || 0x00 || KEK)[0..16]
```

- 标签不同 → 派生出完全不同的子密钥（域分离）；
- `0x00` 分隔符 → 避免标签与密钥拼接产生歧义；
- 用 SM3 而非 HKDF：仓颉标准库与 stdx 均无 HKDF，单步 SM3 派生已满足
  「从一把主密钥派生出用途受限的子密钥」这一需求。

### 4.3 自描述与向后兼容

`alg` 编码进 `storageKey`：`"keyId:v1"`（alg=1） vs `"keyId:v1:a2"`（alg=2）。
解包时按 `WrappedKey.alg` 选择派生方式 —— **包裹结果自带算法信息**，
无需外部约定即可解开。

> **兼容性影响**：alg=1 格式的旧包裹数据仍可解开（`unwrap` 按 `alg` 分派），
> 但**新产生的数据一律是 alg=2**。若已存在 alg=1 的生产数据，
> 需执行一次「重包裹（re-wrap）」迁移：解开旧包裹 → 用 alg=2 重新包裹。
> 本项目尚未产生生产数据，暂不需要迁移脚本。

### 4.4 验证

新增 7 个用例（`packages/ams-crypto/tests/key/key_test.cj`）：

| 用例 | 验证点 |
| --- | --- |
| `testWrapUnwrapRoundTrip` | 包裹→解包往返一致；默认 alg=2 |
| `testStorageKeyEncodesAlg` | alg 编码进 storageKey（自描述） |
| `testTamperedCiphertextRejected` | 篡改密文 → 拒绝 |
| `testTamperedMacRejected` | 篡改 MAC → 拒绝 |
| `testWrongKekRejected` | 错误 KEK → 拒绝 |
| `testKeySeparation` | encKey ≠ macKey 且都 ≠ KEK |
| `testDerivationIsDeterministic` | 派生稳定（否则无法解密） |

## 5. 性能影响

| 操作 | GCM（不可用） | CBC + HMAC-SM3 | 相对开销 |
| --- | --- | --- | --- |
| 加密 1 KB | — | SM4-CBC ≈ 1× + HMAC ≈ 0.1× | ~1.1× |
| 解密 1 KB | — | SM4-CBC ≈ 1× + HMAC ≈ 0.1× | ~1.1× |
| 密钥包裹 | — | 每次 2 次 SM3（派生）+ 1 次 CBC + 1 次 HMAC | 密钥操作低频，可忽略 |

**结论**：相对 GCM 的理论开销约 10%，且因 GCM 不可用而**无对比基准**。
对档案管理场景（读多写少、附件体积大）**不构成瓶颈**。

## 6. 未来演进路径

若上游 stdx 修复 SM4-GCM（可跟踪
[Cangjie/cangjie_stdx](https://gitcode.com/Cangjie/cangjie_stdx) 的 issue），
可按以下步骤升级，**不影响已有数据**：

1. `CryptoProvider` 增加 `CipherMode.Gcm`；
2. `AttachmentCipher` 的 `alg` 字段新增取值 `2 = SM4-GCM`，
   密文头部预留了 alg 位，**新数据可用 GCM 写，旧数据仍按 alg=1 读**；
3. 密钥包裹同理，`alg` 新增 `3 = SM4-GCM`；
4. 保留 EtM 读路径，直至所有数据完成重加密。

**因为密文头部带 `alg` 标识、密钥包裹带 `alg` 标识**，算法升级是**可灰度**的，
不需要数据迁移窗口。
