# 15 · 家庭成员邀请（FR-ACL-010）三处待定项评估

> 本文是 `docs/14-家庭成员邀请设计.md` 的**前置决策文件**。
> 设计稿已把「怎么做」写清楚了，但留了三处必须拍板的分叉：§6 授权粒度、§13 R6 审批流、§14 分批范围。
> 本文对每一处给出候选方案、成本/风险/收益对比与**明确推荐**，定稿后回写到 `docs/14`。
>
> 核对基线：2026-10-29，代码与数据库实际状态（不是纸面设计）。

---

## 1. 先说结论

| 决策点 | 推荐 | 一句话理由 |
| --- | --- | --- |
| §6 授权粒度 | **方案 B：主体 + 条目；分类降级为「同主体内按分类收窄」** | 家庭场景的真实诉求是「整个人的档案」或「某一张证」；跨主体分类是伪需求，却要动 `subject_id` 可空，直接动摇全系统的归属锚点 |
| §13 R6 审批流 | **不做** | 邀请方向本就是 owner 主动发起 → 被邀请人接受，这已是一次双方确认；加「申请入组」反而开出「任何人可向任意组投递申请」的新骚扰/枚举通道 |
| §14 分批 | **3 批**（原 4 批合并） | 原方案 F1 完成后「成员零可见」，是不可验收的半成品；改成每批都收在可演示的闭环上 |

**总工作量**：约 17~20 个文件改动，其中 1 处是全局风险点（`ItemRepo.list/count` 的授权下推）。

## 2. 代码现状核查（为什么不能按纸面设计直接开工）

设计稿 §6 假设「三种粒度相互独立，各有 `resource_type` + `resource_id`」。**实际代码不是这样**。核查结果：

### 2.1 `acl_grants` 表（FR-ACL-008 已落地）

```
id            bigint     NOT NULL
subject_id    bigint     NOT NULL   ← 主体必填，不可空
item_id       bigint     NULL       ← 可选收窄
category      smallint   NULL       ← 可选收窄
grantee_id    bigint     NOT NULL
perm_codes    varchar    NOT NULL
granted_by    bigint     NOT NULL
granted_at    timestamptz NOT NULL
expires_at    timestamptz NULL
revoked_at    timestamptz NULL
revoke_reason varchar    NULL
```

这是「**主体为轴 + 可选用条目/分类收窄**」的模型，**不是**三个平等粒度。

### 2.2 `Grant.covers()` 的真实语义（`ams-security/src/authz/authorizer.cj:286-296`）

```cangjie
// 条目级授权：必须条目 ID 相同
if (this.itemId != "") {
    return this.itemId == resource.itemId      // ← 命中即放行，跨主体也行
}
// 分类级授权：分类码相同（category=0 表示不限分类）
if (this.category != 0 && this.category != resource.category) {
    return false
}
// 主体级：必须同主体
return this.subjectId == resource.subjectId     // ← 分类匹配后仍然要求同主体
```

**关键事实**：`category` 分支匹配通过后**没有 return**，而是继续落到主体比较。
即 ——「分类授权」当前**只能在同一个主体内收窄**，设计稿写的「跨主体，按类目共享」**并不存在**。

### 2.3 列表查询完全不看 `acl_grants`

`ItemRepo.list()` / `count()` 的 WHERE 只有一条归属条件：

```sql
AND subject_id IN (<accessible subject ids>)
```

而 `listAccessibleSubjectIds()` 的取值是：

```sql
SELECT DISTINCT id FROM arc_subjects
WHERE deleted_at IS NULL AND (owner_id = ? OR ? = ANY(custodian_ids))
```

**`acl_grants` 从未参与**。全站 12 处调用点（`items.cj:314`、`search.cj:81`、`export.cj:108`、`me.cj:142/418`、`fielddefs.cj:408`、`attachments.cj:475`、`permissionpreview.cj:100`、`itemtemplates.cj:215` …）都是同一口径。

**后果（已存在的 FR-ACL-008 缺口）**：被 `acl_grants` 显式授权的条目，**详情页打得开**（`findByIdRaw` 不过滤主体 + `Authorizer` 放行），但**列表里看不到**、**搜不到**、**导不出**。也就是说 FR-ACL-008 目前只完成了「详情可用」，列表侧是断的。

> 这一点直接决定了 §6 的推荐：不管选哪个粒度，**列表下推都必须做一遍**，这是绕不过去的地基工程。

### 2.4 `custodian_ids` 有列、有读路径、**没有写入入口**

- 列：`arc_subjects.custodian_ids bigint[] NULL`
- 读：`subject.cj:64/85`、`user.cj:742` 都已支持 `? = ANY(custodian_ids)`
- 语义：`subject.cj:22` 注释明确「代管人（custodian）可读不可改」
- **写**：`SubjectRepo` 只有 `update()`（name/alias/relation/summary）与软删除，**全仓没有任何 API 或仓储方法写入 `custodian_ids`**

**后果**：「主体级共享」的数据结构与读路径现成可用，但缺一个「授予/撤销代管」的写入口。这是三档里成本最低的一档。

### 2.5 三档粒度的真实成本表

| 粒度 | 表结构 | 判定语义 | 列表可见 | 缺什么 | 成本 |
| --- | --- | --- | --- | --- | --- |
| **主体** | ✅ `custodian_ids` 已有 | ✅ `ANY(custodian_ids)` 已通 | ✅ 现成 | **写入口**（授予/撤销 + 授权校验 + 审计） | **低** |
| **条目** | ✅ `item_id` 可空 | ✅ `itemId` 命中即放行 | ❌ 列表断裂 | **列表 UNION** + 授权 CRUD 收紧 | **中** |
| **分类（跨主体）** | ❌ `subject_id` NOT NULL | ❌ 仍要求同主体 | ❌ | 改表 + 改语义 + 改 SQL + 索引重建 | **高** |

## 3. 决策一 · §6 授权粒度

### 方案 A：只做主体级

成员获得某主体的「代管（只读）」→ 该主体下**全部**条目可见。

- **优点**：完全复用现有列与读路径；没有新的可见性语义；`Authorizer` 一行都不用改
- **缺点**：不能「只给看学历，不给看健康」
- **代价**：约 3 个文件（`SubjectRepo.grantCustodian/revokeCustodian` + `FamilyRoutes` 授权端点 + 审计动作）

**风险点**：`custodian_ids` 的语义是「代管」，若未来某处把 custodian 当作可写角色，家庭只读共享会被动升级为可写。必须在授予时把「只读」写进设计约束，并在 `Authorizer` 侧确保 custodian 不携带写权限（当前 `subject.cj:22` 的注释保证，但**没有测试守着**）。

### 方案 B：主体 + 条目（推荐）

- 主体级：按方案 A
- 条目级：复用 `acl_grants.item_id`，补**列表下推**（`subject_id IN (...) OR id IN (SELECT item_id FROM acl_grants WHERE ...)`)
- 分类级：**保持现状语义**，即「同主体内按分类收窄」。UI 文案明确写「该主体下的『教育经历』」，**不宣称跨主体**

- **优点**：
  - 覆盖两个真实诉求：「帮我妈管她的证件」（主体）与「只给孩子看这张房产证」（条目）
  - 分类级不需要改表，只是把已有多年的语义**如实写进文档**，不新增风险
  - 顺带修掉 FR-ACL-008 的列表断裂（否则条目级永远只是半个功能）
- **缺点**：列表下推是全局改动，见 §5 风险 R1
- **代价**：约 8~10 个文件

### 方案 C：三档齐全（含跨主体分类）

- 需要：`subject_id` 改可空 → `covers()` 重写 → 列表 SQL 支持 category-only 分支 → 全站 12 处 `subject_id IN (...)` 逐一复核 NULL 语义 → 索引重建
- **优点**：设计稿 §6 完整落地，概念最干净
- **缺点**：
  - **动摇 FR-ACL-006「归属强制」这个全系统锚点**。`subject_id NOT NULL` 是「条目必属于某人」的物理保证，一旦可空，所有按归属过滤的查询都要回答「无主体的条目归谁」
  - 跨主体分类在家庭场景几乎无用：教育经历属于某一个人，不存在「全家共用教育经历」
  - 成本是方案 B 的 2~3 倍，收益接近 0
- **代价**：约 15~18 个文件 + 一次高风险迁移

### 推荐

> **方案 B。**
>
> 判断依据是「归属强制」这条红线：`subject_id NOT NULL` 保证任何条目都能回答「这是谁的档案」。
> 为一个人群里几乎不存在的诉求（跨主体同类目共享）去松动这条约束，是典型的**用架构纯度换运维风险**。
> 分类授权的价值在「同一主体内缩小范围」（给家人看学历、不看健康），这个诉求方案 B 已经满足。

## 4. 决策二 · §13 R6 是否要「成员申请 → owner 审批」

### 方案 A：不做审批流（推荐）

邀请链路保持 **owner/manager 主动发起 → 被邀请人输入邀请码接受**。

- **优点**：
  - 这是一条**方向正确**的链路：谁的数据谁决定给谁看，主动权在数据所有者手里
  - 邀请码本身就是凭据（8 位、短 TTL、一次性、可撤销、失败计数），安全性不依赖审批
  - 不引入新的通知/待办/状态机，不扩大攻击面
- **缺点**：owner 无法「收到申请后统一处理」；但家庭组通常 ≤ 8 人，不构成痛点

### 方案 B：只做「邀请需二次确认」

邀请创建后进入 pending，owner 需在同一会话内确认才下发 code。

- **优点**：听起来更严谨
- **缺点**：**逻辑倒置** —— 发起邀请的人就是 owner 本人，等于「我确认我自己的操作」，纯增摩擦
- **结论**：不推荐，属于形式主义安全

### 方案 C：完整「申请单」模型

任何人都可以向任意组提交入组申请，owner 审批通过后成为成员。

- **优点**：适合「陌生人加入公开协作组」的机构场景
- **缺点（关键）**：
  - **开出新的骚扰与枚举通道**：任意账号可向任意组投递申请，owner 的通知箱会被塞满；申请本身也变成了「这个组存在」的探测信号 —— 与设计稿 §3 的「No Enumeration」原则直接冲突
  - 需要新增：`fam_join_requests` 表、状态机（pending/approved/rejected/expired）、通知模板、审批页、频率限制、批量拒绝
  - 家庭场景没有这个诉求：家里人是你认识的，你直接发码给他
- **代价**：约 6~8 个额外文件，且把「一次确认」变成「两次确认 + 一个可被滥用的入口」

### 推荐

> **方案 A：不做。**
>
> 真正的安全诉求不是「多一道审批」，而是**事后可追溯 + 随时可撤销** —— 这两点由
> F1 的入组审计、F4 的 10 个审计动作码、以及「移除成员 = 同时撤销全部授权并登出会话」共同覆盖。
> 审批流解决的是「我不信任发起人」，而这里发起人就是数据所有者本人。

## 5. 决策三 · §14 分批

### 方案 A：保持原 4 批（F1 组/成员/邀请 → F2 授权+下推 → F3 前端 → F4 审计）

- **问题**：F1 结束时成员**零可见** —— 能拉人进组，但进来什么也看不到。这不是「阶段性成果」，是**不可验收的半成品**：既没法演示，也没法让用户判断方向对不对
- F2 的列表下推又必须在 F1 之后，两批之间存在强耦合的空窗期

### 方案 B：3 批，每批都收在可演示闭环（推荐）

| 批次 | 内容 | 结束时能演示什么 | 文件量 |
| --- | --- | --- | --- |
| **B1** 最小可用闭环 | 迁移 019（`fam_groups`/`fam_members`/`fam_invites` + `acl_grants.group_id`）<br>`FamGroupRepo`/`FamMemberRepo`/`FamInviteRepo`<br>`FamilyService`（建组/邀请/接受/移除）<br>`SubjectRepo.grantCustodian/revokeCustodian`<br>`FamilyRoutes`（组 + 成员 + 邀请 + 主体级授权）<br>前端 `/family` 列表 + 组详情 + 邀请面板 | **拉人进组 → 他能看到我授权的整个主体** | 8~10 |
| **B2** 精细授权 | `ItemRepo.list/count` 加授权 UNION（**全局风险点**）<br>授权 CRUD 收紧（条目级 + 分类收窄）<br>前端授权面板（选成员 → 选范围 → 选有效期） | **只把某一张证给孩子看** | 6~8 |
| **B3** 收口 | 10 个审计动作码落链<br>§12.3 安全用例全跑通<br>`docs/14` 按本文结论定稿回写 | 可交付、可举证 | 3~4 |

- **优点**：B1 结束就是一个能演给用户看的东西；B2 的价值点（精细授权）单独一批，失败也不会拖垮 B1
- **缺点**：B1 略胖（后端 + 前端同时上）

### 方案 C：5 批（把前端拆出去）

B1 后端组/邀请 → B2 后端主体级授权 → B3 前端组/邀请 → B4 后端+前端条目级 → B5 收口

- **优点**：每批更小
- **缺点**：B1/B2 结束时**用户看不到任何界面**，无法验收；前端与后端来回切，上下文成本高

### 推荐

> **方案 B：3 批。**
>
> 依据是「每批必须能被演示」这一条：用户判断方向对不对的唯一方式是**看到东西**。
> 原 4 批里 F1 与 F2 之间存在「能拉人但什么也看不到」的空窗，是最容易做完发现方向错了的结构。

### 批次内的硬约束（沿用设计稿 §14）

每批都必须通过：
- `bash scripts/build.sh` → 0 error
- `npm run build` → 0 error
- `bash scripts/test.sh` → 0 fail
- 新增对应单测；安全用例（§12.3）在 B3 前全部跑通

## 6. 全局风险：B2 的列表下推会同时改变 6 个入口的语义

`ItemRepo.list/count` 是**列表、搜索、导出、批量编辑、权限预览、附件面板**的共同底层。一旦把「授权范围」并入 WHERE：

| 入口 | 现状 | 加入授权后必须回答的问题 |
| --- | --- | --- |
| 档案列表 `GET /api/items` | 只按主体 | 被授权单条目是否出现在「全部主体」视图下？ |
| 搜索 `GET /api/search` | 只按主体 | 搜索结果是否包含授权条目？来源标签怎么标？ |
| 导出 | 只按主体 | 导出「我的全部档案」是否会把别人授权给我的条目打包带走？ |
| 批量编辑 | 只按主体且**要求写权限** | 授权是只读的，必须确认批量写仍然被拒 |
| 权限预览 `countVisible` | 只按主体 | 预览数字会变 —— 这其实是**修正**（原先漏算授权） |
| 附件面板 | 只按主体 | 授权条目的附件能不能下载？（应能，只读） |

**结论**：B2 不是「加个 OR 条件」，而是**一次语义统一**。必须：
1. 抽一个 `AccessScope`（主体集合 + 授权条目集合）作为所有入口的唯一入参，禁止各路由自己拼；
2. 补 1 条跨入口回归用例：同一条授权在 6 个入口的可见性判定**完全一致**；
3. 导出侧单独决策：默认**不把授权条目打进「我的档案」导出包**（避免用户无意识地把别人的数据导出传播），需要在导出页显式勾选。
