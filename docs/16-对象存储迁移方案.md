## 1. 预检：存量附件数与总大小

切换前先在库上跑以下 SQL（列均来自 `001_core_schema.sql` / `025_storage_provider.sql`；
可用 `python scripts/db.py sql -s "..."` 执行，见 compose 注释与 `docs/15`）：

```sql
-- 存量附件行数与总大小（与 countAll() 同一口径：不过滤 deleted_at）
SELECT COUNT(*) AS attachment_rows,
       COALESCE(SUM(file_size), 0) AS total_bytes
FROM arc_attachments;

-- 按平台 / 后端大类分布（025 新增 storage_provider，DEFAULT 'local'）
SELECT storage_provider, storage_backend, COUNT(*) AS rows,
       COALESCE(SUM(file_size), 0) AS total_bytes
FROM arc_attachments
GROUP BY storage_provider, storage_backend
ORDER BY storage_provider;

-- 历史版本表也有独立 storage_key，迁移时不能漏
SELECT COUNT(*) AS version_rows, COALESCE(SUM(file_size), 0) AS total_bytes
FROM arc_attachment_versions;
```

同时记录「定位三元组」快照：`GET /api/admin/storage/config` 的 `provider` / `endpoint` / `bucket`，
以及 `GET /api/admin/storage/providers` 的 `current`。后续任何一步都要能回答「旧对象现在该去哪里找」。

**⚠️ `countAll()` 的真实口径**：`packages/ams-data/src/repo/attachment.cj:742` 是
`SELECT COUNT(*) AS n FROM arc_attachments` —— **不带 `WHERE deleted_at IS NULL`**。
即软删行也计入。因此「库内已有附件」的判定包含已软删但 `storage_key` 仍须保留的历史行。
预估 Conflict 时不要用「当前可见附件数」代替。

## 2. `storage_key` 定位三元组不可变规则

`arc_attachments.storage_key` 只存**对象键**，不含「到哪台后端去找」的信息。
定位靠三元组：**`provider` + `endpoint` + `bucket`**（`storageadmin.cj` 的
`locatorChanged = provider != runtime || endpoint != runtimeEndpoint || bucket != runtimeBucket`）。
三者任一改变，旧行的 `storage_key` 在新后端就找不到对象 —— 这是**静默数据丢失**，
不是启动时能报错的故障，故接口以 Conflict 硬拒。

两套后端的键映射规则不同，迁移时极易踩坑，必须按真实代码区分：

- **本地 FS**：`LocalFileStorage.pathOf()` = `root + "/" + sanitize(key)`，
  `sanitize()` 把 `/`、`\`、`:` 一律换成 `_`，**扁平**、无多级子目录。
  根目录由 `AMS_STORAGE_DIR` / `AMS_EXPORT_DIR` / `AMS_BACKUP_DIR` 指定。
- **对象存储**：`S3StorageConfig.objectUrl(key)` ——
  - `pathStyle=true`：`endpoint/bucket/<prefix>/<sanitizeKey(key)>`
  - `pathStyle=false`（virtual-host）：`bucket.endpoint/<prefix>/<sanitizeKey(key)>`
  - `<prefix>` 是用途隔离前缀，由 `StorageBackends.make(root, purpose, ...)` 的 `purpose` 决定
    （`storage.cj` 注释：`attachments` / `exports` / `backups`）。
  - `sanitizeKey()`（`s3.cj`）把 `\` → `_`、`..` → `_`、控制字符 → `_`，**保留 `/`** 作为合法前缀分隔。

> **关键**：FS 上的扁平文件名是 `LocalFileStorage.sanitize(storage_key)` 的结果（`/` 已变 `_`），
> 而 S3 目标键必须用**原始 `storage_key`** 经 `S3StorageConfig.sanitizeKey()` 组装。
> 不要把 FS 文件名直接当对象键上传。两者规则不同，直接照抄会导致对象键错位。

**不改变三元组时允许改的字段**：凭据（`accessKey` / `secretKey`）、`region`、`pathStyle`
（寻址风格）——`storageadmin.cj` 明确「仅改凭据 / region / 寻址风格不受此限制」。
但注意 `pathStyle` 改变会改变对象 URL 形态，若已有数据仍应谨慎，先验证再切换。

## 3. 桶策略：禁公共读（运维侧动作，代码无法代劳）

- 附件字节在写入后端前已由 `AttachmentService` 做 SM4-CBC + HMAC-SM3 加密（`s3.cj` 头注释），
  对象存储**始终只存密文**；即便如此，桶策略仍必须禁公共读（纵深防御）。
- 本仓**没有**设置桶策略的能力：`S3Transport` 接口只有 `putObject` / `getObject` / `deleteObject`
  （`s3.cj`），集成测试里的「创建桶」只是 `putObject(endpoint/bucket, 空字节)`，不涉及策略。
- 因此「禁公共读」由运维在厂商控制台 / MinIO 策略里设置，并在切换前用**匿名 GET** 验证被拒
  （见 §7 验证清单）。`providers.cj` 的 `huawei` profile 也写明「桶策略禁公共读」。
- **隔离区不迁移**：`QuarantineStorage` 恒定本地 FS（`backendCode()` 返回 0，`storage.cj`），
  FR-ATT-007 的物理隔离不随主后端切换。不要把它搬进对象桶。

## 4. 凭据注入与失败关闭语义

**运行时读取**（`s3.cj` `S3StorageConfig.fromEnv(prefix, provider)`）：
必填 5 项 `AMS_S3_ENDPOINT` / `BUCKET` / `REGION` / `ACCESS_KEY` / `SECRET_KEY`，
缺任一返回 `None`；`AMS_S3_PATH_STYLE` 可选，缺省时取 `providers.cj` 该平台的 `defaultPathStyle`
（MinIO 默认 path-style，云厂默认 virtual-host）。

**失败关闭链**（`storage.cj` `StorageBackends.make` + `s3.cj`）：
1. `StorageProviders.current()` 遇未知 code → `validationError`，不静默回落。
2. 非 `local` 且 `fromEnv()` 返回 `None` → `validationError("AMS_S3_*", "S3 配置不齐备…")`。
3. `cfg.validate()` 校验 `endpoint` 必须以 `http://` / `https://` 开头，AK/SK 非空。
4. 配置完整 → 构造真实 `HttpS3Transport.forConfig(cfg)`；真正的网络 I/O 在首次 `put`/`get` 时发生。
5. 运行期：连接 / 签名 / 响应失败一律抛 `AppError(StorageFailure)`，**404 → `None`**（区分「不存在」与「故障」），
   **绝不静默回落本地 FS 或明文写入**。`UnavailableS3Transport` 兜底桩被调用即抛错，不伪装空内容。

**凭据脱敏与审计**（`storageadmin.cj` / `deployment.cj`）：
- `DeploymentStore.SECRET_KEYS` 含 `S3_ACCESS_KEY` / `S3_SECRET_KEY`，`redactedJson()` 一律遮为 `***`。
- `GET /config`：`accessKey` 经 `maskKey()`（前 4 + `***` + 后 4），`secretKey` 非空恒 `***`。
- 审计 `AuditAction.ConfigChange` 的 detail 只含 `provider` / `endpoint` / `bucket`，**绝不含 AK/SK**。
- 管理页（本轮新增的「系统运维 → 存储平台」）只把脱敏值作占位符展示，凭据输入框默认留空。

**⚠️ 全量覆写 + 空值即删行**：`putConfig` 每次把 7 个键全部写入 `DeploymentStore.setAll()`；
`DeploymentStore.persist()` 跳过空值行，故 **PUT 传空 `accessKey`/`secretKey` 等于从 `deployment.env`
删除该键**，运行时回退到环境变量注入。若原凭据只存在文件里、留空保存，重启后会因缺凭据而失败关闭。
生产环境建议凭据由 compose 环境变量注入（`deployment.cj` 注释亦把 S3 凭据列为敏感键），
此时文件里本就无该行，留空保存无影响 —— 这是管理页「留空 = 不重写」提示的确切含义。

## 5. 逐批复制 + 校验和核对

> **如实前提**：本仓**没有**内置数据迁移脚本 / CLI（只有 §10 的连通性验证脚本）。
> 复制需用运维侧任意 S3 兼容客户端，按 `storage_key` 逐条把 FS 上的密文字节搬到目标桶。
> 本节给的是**步骤与核对口径**，不是可直接粘贴的迁移命令 —— 本仓不提供这种命令。

1. **导出清单**：从 `arc_attachments` 与 `arc_attachment_versions` 取
   `storage_key, file_size, encode(sm3_fingerprint,'hex')`（`attachment.cj` 的查询即用
   `encode(sm3_fingerprint, 'hex') AS fp_hex`），按 `storage_key` 排序、分批（例如每批 N 条）。
2. **定位源文件**：`AMS_STORAGE_DIR` 下 `LocalFileStorage.sanitize(storage_key)` 的扁平文件；
   导出 / 备份目录同理（`AMS_EXPORT_DIR` / `AMS_BACKUP_DIR`）。
3. **组装目标键**：用**原始 `storage_key`** 经 `S3StorageConfig.sanitizeKey()`，
   加用途前缀 `attachments` / `exports` / `backups`，按目标 `pathStyle` 组装 URL。
4. **逐批 PUT**：读源字节 → PUT 到目标桶 → 记录成功 / 失败清单。
   搬运的是**落盘密文字节本身**，不解密、不重加密（对象存储视为不可信介质）。
5. **逐条校验和核对**：
   - 目标对象 GET 读回的**字节数 = `file_size`**；
   - 读回字节的 **SM3 摘要 = `sm3_fingerprint`**（`encode(...,'hex')` 取出比对）；
   - 因为两端是同一份字节，摘要应逐条一致；若口径不符，以「读回字节 vs 库内 fingerprint」逐条比对为准，
     不臆断该摘要是明文还是密文口径（以 `AttachmentService` 落盘实现为准）。
6. **可重入**：`put` 是覆盖写（`StorageBackend.put` 语义「写入（覆盖）对象」），
   `storage_key` 不变，失败批次重跑不会制造重复对象。
7. **一致性复核**：全部批次通过后，再跑一次 §1 的 SQL，确认行数 / 总字节与清单吻合。

**不要漏**：`arc_attachment_versions` 每行有独立 `storage_key`，历史版本下载依赖它；
只搬 `arc_attachments` 会让历史版本下载失效。

## 6. 切换窗口与重启

1. **停写窗口**：暂停上传 / 新建附件 / 导出，避免切换过程中新旧后端各写一半。
2. **写配置**：两种路径，取决于库内是否已有附件（见 §9，**这是本方案的硬约束**）：
   - 库内附件数为 0：管理页「系统运维 → 存储平台」或 `PUT /api/admin/storage/config` 直接选择平台。
   - 库内已有附件：`PUT` 改定位三元组会被 Conflict 拒绝，须按 §9 由运维直接编辑 `deployment.env`。
3. `PUT` 成功返回 `{"updated":true,"requiresRestart":true,"transportReady":...,"hint":"…重启后生效…"}`
   （`storageadmin.cj`）。**配置此时只是落盘，未生效**。
4. **重启 `ams-server`**：compose 项目 `ams`、服务名 `ams`，例如
   `docker compose -p ams -f deploy/compose/docker-compose.yml restart ams`。
   重启时 `main.cj` 的 `storageEnvKeys` 把 `deployment.env` 的 7 个键 `setVariable` 同步进进程环境变量
   → `StorageProviders.currentCode()` 读 `AMS_STORAGE_PROVIDER` → `StorageBackends.make()` 装配新后端。
5. 观察启动日志无 `validationError("AMS_S3_*")` / `StorageFailure`；任一失败即按 §4 失败关闭，不会静默回退。
6. 窗口结束后恢复写入。

## 8. 回滚到 FS 的步骤

**先说硬约束**：把 `provider` 改回 `local` 同样是 `locatorChanged`（`provider != runtime`），
库内已有附件时 `PUT /config` **一样返回 Conflict**。所以回滚不是「再 PUT 一次」。
`QuarantineStorage` 本来就是本地 FS，不需要回滚。

- **路径 A（库内附件数为 0）**：管理页或 `PUT /config` 设 `provider=local`（endpoint/bucket 可空），
  重启即回到 `LocalFileStorage`，零数据搬迁。
- **路径 B（库内已有附件，生产常态）**：
  1. 开停写窗口。
  2. 把对象桶里的对象按 `storage_key` **反向复制**回 `AMS_STORAGE_DIR`（键名用
     `LocalFileStorage.sanitize()` 的扁平规则），逐条按 §5 的口径校验。
  3. 由于 `PUT` 仍会被 Conflict 拒绝，由运维**直接编辑 `ams-config` 卷内 `/app/config/deployment.env`**：
     把 `STORAGE_PROVIDER` 改回 `local`（或删掉该行，让 `AMS_STORAGE_PROVIDER` 环境变量 / 默认 `local` 生效），
     并清理残留的 `S3_*` 行。本仓**没有**对应 HTTP 端点，这是 `storageadmin.cj` 存量保护规则的直接后果。
  4. 重启 `ams-server`，`main.cj` 同步后 `StorageProviders.currentCode()` 得到 `local`。
  5. 按 §7 验证下载往返全部成功。
  6. **确认无误前不要删任何东西**：不要删 `ams-minio-data` 数据卷，也不要删 FS 原文件；
     验证通过后再由运维按保留策略清理对象桶。

## 9. 「库内已有附件时接口 Conflict 拒绝改 provider」的处置路径（重点）

**现象**：`PUT /api/admin/storage/config` 返回 HTTP 409，`message` 为
（`storageadmin.cj` 第 219–220 行原文）：

> 库内已有 N 条附件；切换存储平台或 endpoint/bucket 会使旧 storage_key 失效。
> 请先完成数据迁移，再重试；仅修改凭据 / region / 寻址风格不受此限制。

**根因（真实代码）**：`storageadmin.cj` 第 209–222 行：

```
locatorChanged = provider != runtime || endpoint != runtimeEndpoint || bucket != runtimeBucket
if (locatorChanged) {
    n = attachmentRepo.countAll()
    if (n > 0) throw AppError(Conflict, ...)
}
```

`countAll()` = `SELECT COUNT(*) FROM arc_attachments`，**不过滤 `deleted_at`**。

**⚠️ 必须如实指出的接口缺口**：判定只看 `countAll() > 0`，**不检查数据是否已经迁移完成**，
代码里也没有「迁移完成」标记或豁免开关。因此**按 §5 完成迁移后重试 `PUT` 仍会 Conflict** ——
错误信息里的「再重试」是提示文案，不是代码承诺。这是 `packages/` 侧的现状，本轮不改后端。

**可执行的处置路径**：

1. **先确认附件数**：§1 的 `SELECT COUNT(*) FROM arc_attachments`。
2. **完成数据迁移**（§5）：逐批复制 + 校验和核对，含 `arc_attachment_versions`。
3. **改「不受限」的字段可以用接口**：`PUT /config` 只改 `accessKey` / `secretKey` / `region` /
   `pathStyle`（`provider`、`endpoint`、`bucket` 保持与运行时一致）不受 Conflict 限制 ——
   可借此先把目标桶凭据注入 `deployment.env`。
4. **定位三元组的切换走文件编辑**：在停写窗口内，由运维直接编辑 `ams-config` 卷内
   `/app/config/deployment.env`，写入 7 个键（§0 表格），然后按 §6 重启。
   这是当前实现下唯一能改 `provider`/`endpoint`/`bucket` 且保留存量数据的路径。
5. **全新部署 / 库内附件数为 0**：直接用管理页 `PUT` 选择平台（不触发 Conflict），
   这是最省事的路径 —— 建议**在导入历史数据之前就定好平台**。
6. **绝对禁止**：为绕过 Conflict 而 `DELETE FROM arc_attachments` / 清空附件表（删业务数据），
   或改动 `countAll()` 的口径。前端管理页的「定位三元组锁定」也是基于健康看板
   `storageFiles` 的**前置预判 + 禁用**，权威判定始终在服务端。
7. **后续建议（本轮不实施）**：若需要让「迁移完成后可在线重试」，应在 `packages/` 侧
   为 `putConfig` 增加显式确认或按 `arc_attachments.storage_provider` 逐行判定；
   这属于后端改动，不在本轮范围内。
