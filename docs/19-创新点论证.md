## 1. 间接替代方案的固有短板（公开资料佐证，证据 B）

> 本节所有论断均来自公开资料，仅描述竞品**能力形态**，不给出精确数字；
> 竞品产品持续演进，下列「短板」指其在这些维度上**不构成 AMS 这类组合的差异化能力**。

### 1.1 网盘 / 共享盘
- 传统形态被描述为「文件堆放间」：无组织结构、检索靠个人记忆、权限粗放、分享靠链接谁转发谁都能看（赛凡智云，2025）。
- 现代企业网盘已演进到「标签 + 角色权限 + 日志」（联想 Filez 的「分类 + 分级 + 分区」三维管控、够快云库的字段级权限），
  但其权限与结构是**文档 / 文件夹层面**的，**字段级国密加密 + 盲索引等值检索、私有化零外部依赖 OCR、可携带密码学校验导出**不属于其能力集。
- 引用：<https://www.saifanbox.com/hydt/291.html>、<https://www.filez.com/news/detail/31c8c8a9ae0fabca3f8b8c0a9a09bcf7.html>、<https://www.gokuai.com/press/a4419>

### 1.2 密码管理器
- 专长于**文本凭据**（用户名、口令、API Key、信用卡号、2FA），浏览器自动填充是其核心超能力（vaultine、Keeper、Acer 对比文）。
- 对**真实文件 / 大体积附件**体验差：50 张高清私密照片或 200MB 视频上传笨拙且易触存储上限；**无内置媒体查看器**，须先下载解密才能看（vaultine 对比文）。
- 即使用「安全笔记 / 文件附件」扩展，其设计原点仍是凭据，不是档案生命周期管理。
- 引用：<https://vaultine.app/zh-hans/boke/mima-guanliqi-vs-anquan-baoxianku>、<https://www.keepersecurity.com/blog/2022/06/19/what-is-a-password-manager/>

### 1.3 政务民生 App（纸质档案袋的数字化替代形态）
- 「一网通办」类 App 的「一人一档」由后台归集固定栏目（个人信息类 / 生活档案类 / 证照信息类 / 个人办事类），**不可自定义字段模型**（上海大数据中心公开描述）。
- 数据沉淀在政府云，**用户无导出权、无法私有化自持**；且历史上出现过明文上传账户密码、过度索取权限等被通报案例（人民网·中国日报 政务 APP 个人信息保护系列）。
- 引用：<https://chuangxin.chinadaily.com.cn/a/202012/24/WS5febdeb5a3101e7ce973834e.html>、<https://zwdt.sh.gov.cn/>

### 1.4 通用方案（依赖云端 OCR / 外部进程）
- 通用 OCR / 文档处理普遍走**云端**：图片上传到远程服务器处理，存在留存、模型训练复用、跨法域合规风险（Umi-OCR 离线 vs 在线对比、ScanLens、transcribeall 均指出此点）。
- 对医疗 / 法律 / 金融等强合规场景，部分监管要求**禁止将文档发送到外部服务器**；离线 OCR 在隐私维度「决定性胜出」，仅在复杂排版准确率上略逊。
- 引用：<https://umi-ocr.com/zh-CN/blog/offline-vs-online-ocr>、<https://scanlens.io/zh/blog/on-device-vs-cloud-ocr>、<https://transcribeall.io/knowledge/is_laptop_ocr_safe_for_private_documents.php>

## 2. 同赛道直接竞品：类似的档案 / 文档管理系统（本次补齐，证据 B）

> **为什么单列本章**：§1 的四类是「不同形态的间接替代」，说服力有限——评审最该问的是
> **「同样是档案管理系统，Paperless-ngx / Ente / Everplans / 单位侧电子档案系统和你差在哪」**。
> 本节按四类同赛道产品逐一对照，**并如实写出 AMS 不如它们的地方**（§2.5、§8）。
> 所有描述均来自公开资料 / 官方功能清单 / 国家标准文件，只做定性能力对照，不给精确数字。

### 2.1 自托管文档 / 档案管理系统（Paperless-ngx 及同类）
**代表**：Paperless-ngx（社区开源 EDMS/DMS）、Mayan EDMS、Papra；商业侧 DocuWare、M-Files 为其对照对象。

- **公开能力形态**（官方文档）：以标签 / 通信者 / 文档类型 / **自定义字段**组织文档；Tesseract OCR（官方称覆盖 100 余种语言）+ 全文检索与高亮；PDF/A 长期保存 + 原始件并存；单条目下保留多版本；可分享公开链接并设置过期；**多用户权限系统（全局 + 按文档/对象）**；文档变更审计日志；工作流与 OIDC；可导出、数据本地存储不上传第三方。
- **与 AMS 的关键差异（如实）**：
  - 第三方评测明确指出 **Paperless-ngx「stores documents plain on disk / stores documents in clear text by design」**——**明文落盘是其架构选择**，应用级静态加密需由运维用加密卷 / 加密备份 / 网络隔离在基础设施层补齐；AMS 是**字段级 SM4 加密 + SM3 盲索引**落在应用层（`docs/03` §4.3）。
  - OCR 依赖 **Tesseract 外部引擎**，Office / 邮件解析依赖 **Apache Tika / Gotenberg 容器**，官方文档还提供**可选的 Azure AI 远程 OCR**；AMS 媒体链路在 `ams-server` **单进程内**、运行时零外部进程（`README.md:88`）。
  - 其模型是**「文档 / 文件」为中心**（一份文档 + 一组元数据），不是 **「个人全生命周期 11 类档案 + 字段级敏感度分级」**（`useCatalog.ts:39-49`）。
  - 公开功能清单中**未见国密算法对齐、盲索引密文等值检索、失败关闭（密钥缺失即抛错）**。
- **AMS 明显不如它的地方（必须如实写）**：OCR 语言覆盖（本仓字典仅 220 汉字 + 10 手写数字）、机器学习自动分类 / 标签建议、AI 语义检索、多容器工作流与脚本生态、社区成熟度与第三方集成数量。
  本仓 OCR 是**构建期字模查表**（`scripts/gen-media-glyphs.py`），能力面远窄于通用 OCR 引擎。
- 引用：<https://docs.paperless-ngx.com/>、<https://www.opentechhub.io/paperless-ngx/>、<https://thenewstack.io/if-you-need-a-documentation-manager-paperless-ngx-is-the-way-to-go/>、<https://bluefoxconsultant.com/en/blog/blue-fox-articles-2/paperless-ngx-an-open-source-solution-for-document-management-in-smes-212>

### 2.2 端到端加密自托管影像 / 保险库（Ente 及同类）
**代表**：Ente Photos（E2EE、可自托管、Legacy Contacts）、Nextcloud（+E2EE app）、Immich / PhotoPrism / Seafile / Cloudreve（自托管但默认非 E2EE）。

- **公开能力形态**：**端到端加密 + 零知识**，数据在设备端加密后上传，服务端只存密文；跨端客户端、家庭共享 / 共享相册、**Legacy Contacts（身后指定联系人）**；Ente 可自托管且开源、有安全审计。
- **与 AMS 的关键差异 —— 这是取舍，不是优劣（重点）**：
  - 公开资料明确指出 **E2E 零知识的代价是「服务端无法读取内容，因此无法提供语义检索 / 人脸分组 / AI 分类」**（Ente 的 AI / 人脸能力放在设备端）。
  - AMS 选择的是**「服务端可解密字段 + SM3 盲索引」**模型：用**可等值检索**换隐私强度——敏感字段虽 SM4 加密落库，但服务端持有派生能力，可据此做等值查询。
    **这在隐私强度上弱于 E2E 零知识**，换来的是服务端检索、结构化筛选与审计能力。二者是**不同信任模型下的取舍**，本文不作「谁更安全」的单向结论。
  - 这类产品以**照片 / 视频 / 文件**为中心，不是字段级结构化档案；且 E2EE 环境下「字段级授权到具体档案条目」的形态与 AMS 不同。
- **AMS 明显不如它的地方**：零知识隐私模型、跨端原生客户端成熟度、大容量影像备份体验、第三方安全审计。
  AMS 的鸿蒙客户端为自研纯 ArkTS，生态与打磨程度不及成熟商业产品（`mobile/README.md` 亦自述存在功能降级项）。
- 引用：<https://www.ente.io/>、<https://www.dreamhost.com/guides/immich/immich-or-photoprism-ente-nextcloud>、<https://use-apify.com/blog/google-photos-alternatives-2026>、<https://opensourceprojects.cc/alternatives/microsoft-onedrive>

### 2.3 数字遗产 / 家庭档案 SaaS（Everplans、Trustworthy 及同类）
**代表**：Everplans、Trustworthy（Family Operating System）、Cake、My Life & Wishes。

- **公开能力形态**：**数字保险库**归集遗嘱 / 保险 / 健康 / 账户 / 重要证件，按主题（个人信息 / 医疗 / 财务法律 / 身后安排等）组织；**按主题或子分类授予可信代理人查看权限**；清单引导、重要日期提醒、身后访问。
- **与 AMS 的相似点（必须先承认）**：这类产品与 AMS 的**目标人群最接近**——都是「个人 / 家庭重要资料 + 授权给可信的人」，AMS 的**家庭组三级授权**（`docs/12`）与「一人一档」式组织在目标上与其同源。
- **关键差异（如实）**：
  - **托管 SaaS + 订阅制**，用户不私有化自持；公开评测甚至建议用户**定期下载 / 打印做物理备份**，因为此类服务可能被收购或关停——与 AMS「完全数据自持 + 可携带导出包（HMAC-SM3 验签）」形成直接对照。
  - 授权粒度是**主题 / 文件夹级**，不是**条目级 / 分类级 / 单条三级 + 字段级敏感度**（`README.md:107-115`）。
  - 公开资料中**未见国密算法对齐、字段级加密与盲索引、可校验审计哈希链、失败关闭**。
- **AMS 明显不如它的地方**：开箱即用的引导式清单、身后事务流程与法律资源、面向非技术用户的成熟度与内容运营；AMS 是**私有化工程产品**，需要用户自行部署与运维（虽有图形化启动器，`docs/09`）。
- 引用：<https://www.everplans.com/>、<https://www.everplans.com/articles/guide-how-to-securely-store-and-share-your-information-and-documents>、<https://www.care.com/c/best-online-end-of-life-planning-and-document-services/>、<https://www.seniorliving.org?p=233993/>

### 2.4 单位侧电子档案 / 干部人事档案系统（有国家标准的正规军）
**代表**：符合国家档案局《电子档案管理系统基本功能规定》与 **GB/T 33870-2017《干部人事档案数字化技术规范》**的电子档案管理系统。

- **公开能力形态（国标 / 规范）**：十大类固定分类与档号规则；**密级**等同纸质档案；RBAC 分「管档人 / 查阅人 / 审批人 / 系统管理员」且**权限互斥**；「**线上申请—分级审批—限时授权**」的利用流程；防下载 / 防复制 / 防截屏的**动态水印**（含查阅人姓名 / 时间 / IP）；全量操作日志（保存不少于 3 年）、可选区块链存证；真实性 / 完整性 / 可用性 / 安全性检查；多条件模糊 / 精确 / **全文检索**与跨全宗递进检索；按国家标准格式输出、XML 数据交换与 3-2-1 备份。
- **与 AMS 的根本定位差异（最需要说清）**：
  - **数据主体是组织 / 单位，个人是被归档的对象**，不是数据的所有者；规范强调**「防下载、防拷贝、防截屏」「最小知悉范围」「涉密设备不得连接互联网」**。
  - AMS 恰好相反：**个人 / 家庭是数据主体**，核心承诺是**完全数据自持 + 可携带导出 + 离开原系统仍可验证**（`README.md:92-98`、`docs/03` §6.5）。**两者的「导出权」方向是相反的**。
  - AMS **明确不做审批流**（`docs/12` R6 决策：不引入审批流），也未做密评 / 等保测评（`SECURITY.md:39`）。
- **AMS 明显不如它的地方（必须如实写）**：有国家标准与行业规范背书、密级体系、审批工作流、涉密环境与物理安全要求、长期保存与移交制度。
  **AMS 不是、也不能替代单位侧电子档案系统**；它面向的是「个人 / 家庭私有化自持」这一不同场景。
- 引用：国家档案局《电子档案管理系统基本功能规定》<https://www.saac.gov.cn/daj/gfxwj/201910/0ae864936c3a49d1abde0e618dc47044/files/662022358a8542f78032c2b5c1ac4775.pdf>、
  GB/T 33870-2017 全文（转载）<http://mp.weixin.qq.com/s?__biz=MzU1MTMzMjM5Ng==&mid=2247490144&idx=2&sn=f39627931b259d0218be81c4c1196219>、
  <https://www.yfda.cn/dabk/45434.html>、<https://www.yfda.cn/hyxx/41006.html>

### 2.5 同类系统对照带来的「反向边界」（防止自我吹捧）

对照完四类同赛道产品后，必须承认以下三点，否则论证不成立：

1. **AMS 不是通用文档管理系统的替代品**：Paperless-ngx 在 OCR 语言覆盖、ML 自动分类、工作流、社区生态上明显更强；
   AMS 的取舍是**牺牲通用性，换字段级国密 + 进程内零依赖媒体链 + 可举证审计**。
2. **AMS 的隐私强度不是最高**：E2E 零知识产品（Ente）服务端完全无法读取内容，强于 AMS 的「服务端可解密字段」模型；
   AMS 以隐私强度换**可等值检索与结构化筛选**，这是设计取舍而非优势宣告。
3. **AMS 不是合规档案系统**：单位侧电子档案有国标、密级、审批流与涉密环境要求；AMS 未做密评 / 等保测评、明确不做审批流，
   定位是**个人数据主体自持**，不能用于组织侧法定归档。

> 因此，§4 / §5 论证的是**「在特定细分场景下的能力组合独特性」**，不是「全面超越同类产品」。

## 3. AMS 的技术解法与可查证证据（证据 A）

> 本节的「机制」均来自已落地代码与文档，「实测支撑」为可复现的内部指标，标注口径。

### 3.1 结构化档案模型（11 类）
- **机制**：`web/src/composables/useCatalog.ts:39-49` 定义 11 类编码化档案模型：
  个人基本信息(1) / 证件信息(2) / 教育经历(3) / 职业经历(4) / 资质证书(5) / 联系方式(6) /
  家庭关系(7) / 健康信息(8) / 资产信息(9) / 影像附件(10) / 自定义分类(11)；每类带 `sensitivity` 敏感度分级。
- **证据**：`docs/06-数据模型设计.md`（实体 / 字段 / 索引 / 字典）；分类中文名唯一口径以 `docs/06 §12.3` 为准。
- **实测支撑**：11 类模型 + 敏感度分级在前后端源码与 i18n 三语同步（中 / 英 / 法）。

### 3.2 字段级国密 + 盲索引
- **机制**：高敏字段（证件号 / 手机 / 银行卡）`SM4-CBC/CTR` 加密落库；另存 `SM3` 盲索引列做密文等值查询；密钥不经服务端明文落库（`docs/03-安全设计专章.md` §4.3）。
- **证据**：`README.md:35`、`docs/03` §4.2–§4.3；`SM4` 为 `CBC/CTR + HMAC-SM3` 的 EtM 组合（因 stdx 不支持 GCM，见 `docs/08`）。
- **实测支撑**：SM3 / SM4 / HMAC-SM3 与国标标准向量**逐字节一致**（`scripts/verify-stdx.sh` 14 项全过，见 `docs/README.md` 基线）；PBKDF2-HMAC-SM3 迭代派生口令密钥（`docs/03` §4.1）。
- **取舍提示**：本模型让服务端可解密字段，隐私强度低于 §2.2 的 E2E 零知识，换来密文等值检索能力。

### 3.3 细粒度授权（条目级 / 分类级 / 单条三级）
- **机制**：条目级共享链接（不可预测 token、可选访问密码、失败上限、有效期、高敏条目连签发机关都不给）+ 家庭组三级授权（默认只读）；成员角色与全局 RBAC 完全隔离（`docs/12`）。
- **证据**：`README.md:107-115`、`docs/12-家庭成员邀请.md`（含推荐结论：方案 B，主体 + 条目，分类为同主体内收窄）。
- **实测支撑**：共享链接与家庭组授权已在 Web 与鸿蒙客户端双端落地，管理页 `SystemView` 可配置。

### 3.4 可举证审计链 + 可携带导出包
- **机制**：每条审计含前序哈希，可校验链完整性，审计本身也被审计；导出包 `HMAC-SM3` 验签，离开原系统仍可验证（`README.md:112-115`、安全 §6.5）。
- **证据**：`README.md:112-115`、`docs/03` §6.5（四层管控 / 分级策略 / 产物保护 / 限流 / 告警 / 12 条测试用例）。
- **实测支撑**：导出任务走统一异步任务表（`docs/02` §6.3.1），崩溃可恢复。

### 3.5 纯仓颉进程内媒体引擎（零外部依赖）
- **机制**：PNG / BMP / JPEG 解码、PDF 抽文本与图像流、三路 OCR、缩略图、像素水印**全在 `ams-server` 进程内**完成；构建期生成字模，运行时不读系统字体 / 不起外部进程 / 不需 Python（`README.md:88`、`docs/README.md:49-51`）。
- **证据**：`packages/ams-core/src/media/`（png.cj / ocr.cj / pdftext.cj / media.cj）；`scripts/media_worker.py` 仅为离线参考实现，**不参与运行时主链路**。
- **实测支撑**：媒体主链路单测 `packages/ams-core/tests/media/media_test.cj`；字模 220 个常用汉字 × 8 字体原型 + 10 个手写风格数字 × 9 原型（`scripts/gen-media-glyphs.py`）。
- **能力边界提示**：字模查表覆盖面远窄于 §2.1 的通用 OCR 引擎（官方称 100 余种语言），不可对外宣称通用 OCR 能力。

### 3.6 失败关闭 + 存储可插拔 + 存量保护
- **机制**：密码学原语缺失即抛错不降级（`docs/13:72`）；8 个存储平台可切换，库内已有附件时改 provider / endpoint / bucket 一律 Conflict 拒绝，防旧 `storage_key` 静默失效（`docs/16`）。
- **证据**：`README.md:38`、`docs/16-对象存储迁移方案.md`、`docs/README.md` §六 Q2。
- **实测支撑**：`arc_attachments.storage_provider` 自报厂商（`docs/16` 迁移 025）；`S3Transport` 真实 HTTP 层已落地、404→None 其余失败关闭。

## 5. 创新点二：现有方案没有的组合优势（`docs/17` §4.2 详版）

**判定：✅ 可提炼五条可查证的组合优势，且有公开资料定性对照（本文 + `docs/17` §4.2）。**

> 以下五条均为**能力组合的独特性**论证，每条附机制、证据、边界与对照；
> 不构成市场结论（见 §8），且须与 §2.5「反向边界」合读。

### 5.1 字段级国密 + 盲索引
- **机制**：敏感字段 SM4 加密，证件号走盲索引（可等值查询、服务端不可逆推），密钥不经服务端明文落库。
- **证据**：`README.md:35`、`docs/03` §4.3。
- **边界**：依赖 openGauss 密态能力或应用层盲索引；SM2 未实现，导出包签名为对称 HMAC-SM3（`docs/13`）；隐私强度低于 E2E 零知识（§2.2）。
- **对照**：§1 四类间接方案与 §2 四类同类产品的公开功能清单中，均未见「字段级国密 + 盲索引 + 密钥不自持」组合（§1 / §2.1 / §2.3 / §2.4）。

### 5.2 最小暴露的共享模型
- **机制**：条目级共享链接（不可预测 token、可选访问密码、失败上限、有效期、高敏条目连签发机关都不给）+ 家庭组三级授权（默认只读）；成员角色与全局 RBAC 完全隔离。
- **证据**：`README.md:107-115`、`docs/12`。
- **边界**：共享链接仍可被转发，靠访问密码 + 失败上限 + 有效期收敛风险，非绝对防泄漏。
- **对照**：网盘共享为「链接即看」、密码管理器共享为「保险库对保险库」、数字遗产 SaaS 为「主题级授权」（§1.1 / §1.2 / §2.3）；单位侧为「申请—审批—限时授权」流程（§2.4，AMS 明确不做审批流）。

### 5.3 可举证的审计链 + 可携带导出包
- **机制**：每条审计含前序哈希可校验链完整性，审计本身也被审计；导出包 HMAC-SM3 验签、离开原系统仍可验证。
- **证据**：`README.md:112-115`、`docs/03` §6.5。
- **边界**：导出包验签只证明未被篡改，不证明导出时授权合法（需配合审计）；签名为对称 HMAC-SM3，不支持第三方公钥验签。
- **对照**：网盘有日志但不可密码学校验链；政务 App 有留痕但不可携出；数字遗产 SaaS 评测反而建议用户自行下载 / 打印备份（§1.1 / §1.3 / §2.3）；单位侧电子档案强调**防下载防拷贝**，方向相反（§2.4）。

### 5.4 纯仓颉、零外部依赖的媒体链路
- **机制**：PNG / BMP / JPEG 解码、PDF 抽文本与图像流、三路 OCR、缩略图、像素水印全在 `ams-server` 进程内；构建期生成字模，运行时不读系统字体 / 不起外部进程 / 不需 Python。
- **证据**：`README.md:88`、`docs/README.md:49-51`、`packages/ams-core/src/media/`。
- **边界**：CJK OCR 字典仅 220 字、手写仅 10 个近似数字、像素水印不阻止截图翻拍（`SECURITY.md`）；**覆盖面远窄于通用 OCR 引擎**（§2.1）。
- **对照**：通用方案依赖云端 OCR / 外部进程（§1.4）；Paperless-ngx 依赖 Tesseract + 可选 Tika / Gotenberg / 远程 Azure AI（§2.1）。

### 5.5 失败关闭 + 存储可插拔 + 存量保护
- **机制**：密码学原语缺失即抛错不降级；8 个存储平台可切换，库内已有附件时改 provider / endpoint / bucket 一律 Conflict 拒绝，防旧 `storage_key` 静默失效。
- **证据**：`README.md:38`、`docs/16`、`docs/README.md` §六 Q2。
- **边界**：8 个平台中仅 `local` 完全可用，云 OBS 需厂商侧桶策略与 AK/SK 在控制台落实（`docs/16` Q2 结论）。
- **对照**：通用托管方案在密钥缺失时往往降级或回退明文（§1.4）；自托管 DMS 的静态加密依赖运维在基础设施层补齐，不属应用层失败关闭契约（§2.1）。

3. **同赛道产品的反向优势（本次补充的核心边界，§2.5）**：
   - Paperless-ngx 等自托管 DMS 在 **OCR 语言覆盖、ML 自动分类、工作流、社区生态**上明显强于 AMS；
   - Ente 等 **E2E 零知识产品的隐私强度高于 AMS** 的「服务端可解密字段」模型，AMS 以隐私强度换可检索性；
   - **单位侧电子档案系统有国标、密级与审批流**，AMS 未做密评 / 等保测评、明确不做审批流，
     **不能用于组织侧法定归档**；
   - 数字遗产 SaaS 在引导式清单与身后事务运营上更贴合非技术用户，AMS 需自行部署运维。
4. **已知能力边界**（每条优势都附带）：
   - OCR 字典仅 220 字、手写仅 10 个近似数字（`SECURITY.md`）；
   - 像素水印不阻止截图翻拍；短信网关异步投递后端无法同步感知；
   - SM2 未实现、导出包签名为对称 HMAC-SM3，不支持第三方公钥验签（`docs/13`）；
   - 8 存储平台中仅 `local` 完全可用，云 OBS 需厂商侧落实桶策略与 AK/SK（`docs/16`）。
5. **合规红线**：「技术对齐国密（SM3/SM4/HMAC-SM3 与国标向量逐字节一致）」**不等于**
   「取得商用密码产品认证 / 密评 / 等保测评」；进入信创采购目录须另行送检
   （`SECURITY.md:39`、`docs/13:60,66-71`）。本文任何处均不得改写为「已通过认证」。

## 9. 结论

AMS 在「**个人 / 家庭全生命周期数字档案私有化自持**」这一细分场景，提供了一组**同赛道产品与间接替代方案均不构成的能力组合**：
**字段级国密 + 盲索引、最小暴露的共享模型、可举证审计链 + 可携带验签导出、纯进程内零依赖媒体链路、
失败关闭 + 存储可插拔 + 存量保护**。

与同赛道产品对照后，定位可以收得更准：**它不是通用文档管理系统（§2.1）、不是零知识影像保险库（§2.2）、
不是数字遗产 SaaS（§2.3），更不能替代单位侧合规档案系统（§2.4）**；它选择的是
「**以可检索性 / 结构化 / 可举证为优先，接受服务端可解密字段这一隐私取舍，并要求用户自行私有化部署**」的路线。

这些组合的差异化成立，且均有本仓代码与实测证据支撑（§3 / §6）；与公开竞品的对照（§1 / §2 / §7）
进一步说明其定位，同时明确了 §2.5 / §8 的反向边界。所有主张均严守红线：不宣称「业界首个 / 唯一」，
不把算法对齐写成合规认证，不编造第三方基准数字。若需把「设计取向对照」升级为可对外引用的市场结论，
须补充第三方基准测试与真实用户 / 客户验收数据（见 `docs/17` §5.3 已知缺口）。
